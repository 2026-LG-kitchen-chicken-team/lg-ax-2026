# 실제 CLI → KITCHEN AX 공장 화면 테스트

v22 대시보드를 별도 폴더에서 빌드하고, 정이량의 **설치된 상품기획 하네스**를 관찰하는 수동 인수 절차입니다. PR 등록·빌드 통과와 실제 CLI 업무 성공은 별개입니다. 현재 실제 업무 연결 테스트는 미실행입니다.

## 1. 대시보드 준비 — 처음 한 번

이 PR의 브랜치 `codex/dashboard-shin-jinha-v22-pr-20261017`를 별도 폴더에 받습니다. 기존 하네스 설치본·업무 checkout·다른 저장소를 덮어쓰지 않습니다. GitHub에서 이 브랜치의 ZIP을 받아도 됩니다.

팀 저장소 루트에서 PowerShell:

```powershell
$dashboard = (Resolve-Path './대시보드 신진하/versions/v22-20261017').Path
Set-Location -LiteralPath $dashboard
npm.cmd ci
node ./node_modules/vite/bin/vite.js build
```

성공하면 `$dashboard/dist/index.html`이 생깁니다. 제품 하네스는 그 설치본 README의 의존성 준비·로그인·권한 확인을 먼저 마친 상태여야 합니다. 대시보드 빌드가 제품 설치를 대신하지 않습니다.

## 2. 관찰기를 먼저 켜기 — 첫 번째 PowerShell

위 PowerShell에서 `$product`만 **실제로 사용할 릴리즈를 설치한 codex 폴더의 절대 경로**로 지정합니다. 이 PC에서 파일 지문·가상환경 준비까지 확인한 경로 예시는 아래와 같습니다. 폴더 이름만으로 설치 릴리즈 버전이나 최신 여부를 확정하지 않습니다.

```powershell
$product = 'C:/Users/user/Documents/Codex/LG-AX-product-v0.15.0-20261016/codex'
python "$dashboard/tools/start_release.py" --workspace "$product" --dist "$dashboard/dist" --port 8033
```

자동으로 열린 [로컬 공장 화면](http://127.0.0.1:8033/)을 사용합니다. 첫 번째 창은 계속 열어 둡니다. 이 실행은 읽기 서버·관찰기만 시작하며, Codex나 업무 질문은 시작하지 않습니다. 선택 설치본의 제품 파일을 설치 기록과 대조하고, 관찰기는 해당 설치 폴더의 관측 파일을 갱신합니다.

- 포트 사용 중이면 기존 작업을 강제 종료하지 말고 `--port 8034` 등 다른 포트로 다시 실행합니다. 화면 주소도 같은 포트입니다.
- 이미 시작한 CLI 세션을 관찰하려면 명령 끝에 `--latest`를 추가합니다. 선택 폴더의 가장 최근 Codex 세션을 따르므로 다른 세션과 혼동하지 않도록 확인합니다.
- 기본값은 **관찰기를 켠 뒤 시작하는 새 세션 대기**입니다. 먼저 켜 둔 세션은 기본 명령의 대상이 아닙니다.
- 정이량 PC의 CLI를 시험한다면 이 명령과 다음 CLI를 그 PC에서 실행합니다. 다른 PC의 `127.0.0.1`은 그 다른 PC 자신입니다.

## 3. 같은 제품 폴더에서 CLI 시작 — 두 번째 PowerShell

```powershell
Set-Location -LiteralPath 'C:/Users/user/Documents/Codex/LG-AX-product-v0.15.0-20261016/codex'
codex --search --sandbox workspace-write --ask-for-approval on-request
```

첫 창의 `--workspace`와 **정확히 같은 폴더**여야 합니다. 모델·Windows sandbox 등 추가 옵션은 해당 설치본 README와 실행자 설정을 따릅니다. 계정 로그인·프로젝트 신뢰·도구 사용 권한은 실제 CLI 안내에서 확인합니다.

Codex 입력란에 아래와 같이 요청합니다. PowerShell 명령란에 입력하는 문장이 아닙니다.

```text
냉장고 수납·정리·청소에서 사용자가 불편해하는 점을 실제 자료로 조사하고,
해당 모델의 기존 기능과 대조해서 남은 불편과 개선 아이디어 한 개를 보여줘.
근거가 부족하거나 접근이 막히면 그 사실을 알려줘.
지금 수행하는 작업도 짧게 설명해 줘.
```

설치본 기본 catalog는 비어 있을 수 있습니다. 자료 부재·웹 접근 실패·확인 질문·보류도 실제 상태이며, 예제 답이나 성공 사건을 만들어 채우지 않습니다. 이 질문을 제출하면 사용자의 실제 CLI 계정·이용 한도로 업무가 실행됩니다.

## 4. CLI와 화면을 나란히 보며 확인

| 확인 대상 | 기대하는 실제 표시 |
| --- | --- |
| 연결/세션 | 선택한 설치 폴더·세션과 일치. 모션 예시·파일 기록 재생을 실시간 시험으로 사용하지 않음 |
| 현재 작업 | CLI에서 관측한 작업 분류·실행 주체·최근 사건이 오른쪽 현재 작업에 표시 |
| Skill 실행 | 실제 Skill 작업 관측이 있을 때 해당 구역이 주황색으로 커지고 역할별 동작. 다른 구역은 착석 대기 |
| 지침 조회 | 지침을 읽었다는 사실과 실제 Skill 작업 실행을 구분 |
| 병렬 실행 | 실제 동시 작업이 관측된 구역만 함께 확대. 여러 Skill을 목록에 쓰는 것만으로 병렬 실행을 만들지 않음 |
| 진행 수/결과 | 실제로 제공된 수·연결된 결과만 표시. 수가 없으면 집계 전 또는 미제공 |
| 선택/종료 | 다른 방 클릭은 실행 단계를 바꾸지 않음. 종료·취소·연결 끊김·오래된 관측은 실행 강조 해제 대상 |

모든 질문에서 여섯 Skill이 1→6 순서로 켜지는 것은 아닙니다. 필요한 Skill만 사용하며, 메인 AI의 분석·공개 진행 설명과 확인된 Skill 호출은 표시 근거가 다릅니다. 전체 명령 본문·비공개 추론을 그대로 보여주는 터미널 복제 화면도 아닙니다.

## 안 뜰 때 확인 순서

1. `?view=motion`은 모션 예시입니다. 위 런처가 연 로컬 주소로 돌아갑니다. 공개 chatgpt.site 주소만으로 PC의 CLI가 자동 연결되지는 않습니다.
2. 관찰 창이 살아 있는지, 두 창의 제품 폴더가 정확히 같은지, 새 세션을 관찰기 뒤에 열었는지 확인합니다. 기존 세션은 `--latest`로 명시합니다.
3. CLI가 실제 도구 작업 중인지 확인합니다. 로그인·승인 대기·권한 오류·자료 부족은 해결 전까지 실제 처리로 표시할 수 없습니다.
4. 현재 작업은 갱신되지만 방이 커지지 않으면 지침 읽기/CLI 진행 보고인지 실제 Skill 작업인지 표시 근거를 확인합니다. 명령이 끝난 뒤에만 도착한 과거 사건을 실시간 실행처럼 재연하지 않습니다.
5. 수신 갱신 시각과 해당 제품의 `runtime-data/agent-office` 관측 산출물 갱신을 확인합니다. 중복 관찰기 잠금이 있으면 본인이 시작한 기존 관찰기를 정상 종료합니다. 잠금·기록을 임의 삭제하지 않습니다.

첫 창에서 Ctrl+C를 누르면 이번 읽기 서버·관찰기를 닫습니다. 원본 Codex CLI와 다른 작업은 종료하지 않습니다.

## 인수 기록

시험 후 설치본/CLI 버전, 대시보드 커밋, 요청 시각, 현재 작업·활성 Skill·대기/오류·종료 표시, 통과/불일치 항목을 기록합니다. 화면 캡처는 비밀정보·개인 질문 원문을 제외합니다. 원본 인증·세션·DB 전체를 PR에 올리지 않습니다.

2026-10-17 이 PC에서 실행한 것은 런처의 `prepare()` 사전 점검뿐입니다. 설치 파일 지문·관찰용 Python·빌드된 화면 준비가 통과했고 서버/관찰기/업무 모델은 시작하지 않았습니다. 실제 CLI 인수 결과는 사용자가 위 순서로 수행한 뒤 별도 기록합니다.
