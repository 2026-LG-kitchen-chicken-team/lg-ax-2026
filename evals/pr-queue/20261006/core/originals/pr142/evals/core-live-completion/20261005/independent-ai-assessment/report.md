동결된 합성 자료 6사례와 이미 생성된 익명 출력 12개를 같은 기준으로 검토했다. 핵심 결함은 자료 미언급을 기능 부재로 확정한 주장, 기본 정보가 미확인인 채 완료로 끝낸 상태, 원래 가열 충분성 욕구를 다른 욕구로 바꾼 후보 제안이다. 사양 일치만으로 실제 불편이 전부 해소됐다는 결론은 사용 조건에 따라 불확실하게 평가했다. 방법 정체나 라벨의 공통 대응은 추정하지 않았다.

| 사례 | A | B | 익명 판정의 핵심 |
|---|---|---|---|
| HOLD-01 · 패킹 청소 | pass | fail | A는 잔여 접근 불편을 유지하고 두 설계를 가설로 제안한다. B는 같은 불편을 물리적 세정 불가능으로 확대한다. |
| HOLD-02 · 기존 종료 알림 | uncertain | pass | 둘 다 기존 15초 END 표시와의 중복을 피한다. A의 실제 불편 전부 해소 결론은 미확인이다. B는 기능 일치와 인지/가시성 탐색을 구분한다. |
| HOLD-03 · 다른 모델/버전 | pass | uncertain | A는 다른 모델 9.0을 배제하고 대상 1.0 자료 확보까지 보류한다. B의 범위 거절은 맞지만 오류만 있어 실질 판단 품질은 미관측이다. |
| HOLD-04 · 상충하는 얼음 리뷰 | pass | fail | A는 양쪽 경험을 유지하고 조건 확인까지 보류한다. B는 방지 기능 부재를 단정하고 상충/원인 질문을 남긴 채 완료한다. |
| HOLD-05 · 설명서 없음 | fail | pass | A는 핵심 기능 유무를 모르면서 completed/빈 hold_reasons로 끝낸다. B는 unknown과 held, 추가 확인 질문을 일치시킨다. |
| HOLD-06 · 사양 변경 | uncertain | fail | A는 2.0 지원을 인식하지만 목표 온도와 충분한 가열의 조건 일치 없이 불편 전부 해소를 확정한다. B는 실시간 진행도 욕구로 바꾸어 원래 요구와 연결이 부족한 후보를 제안한다. |

pass는 명백한 차단 의미 결함이 없다는 제한된 판정이다. fail은 제공된 근거로 확인할 수 있는 결론을 바꾸는 차단 결함이다. uncertain은 조건 또는 의미 범위가 모호하거나 실질 답변이 없어 통과/실패를 확정할 수 없는 상태다. 모호함이나 단순한 표현 차이를 자동 실패로 처리하지 않았다.

HOLD-01의 리뷰는 “매주 문 고무 패킹을 닦지만 접힌 안쪽 모서리에 빵가루가 남아 손가락을 밀어 넣어야 한다.”이고, 설명서는 젖은 천으로 닦을 수 있으며 사용자 분리 부품이 아니라고 한다. A의 형상·도구 제안은 명시된 청소 방법과 다른 설계 가설이다. A의 insufficient_evidence/unmentioned는 청소 가능성의 부재를 뜻하는지, 모서리 청소 효과의 미확인을 뜻하는지 모호해 관찰 사항으로 남겼다. B의 `$.cases[2].outputs.B.raw_output.concept_assessments[0].reason`은 “모서리 세정이 불가능한 물리적 한계”를 기존 사실로 주장한다. 자료는 불편과 어려운 접근을 보여 주며 세정 자체의 불가능을 입증하지 않으므로 차단 결함이다. 새 평면 패킹이 전부 닦인다는 설명은 proposed 설계의 의도된 효과로 읽었고 검증된 효과로 인정하지 않았다.

HOLD-02의 설명서는 “모든 조리 코스가 끝나면 화면의 END 문자가 15초 동안 깜박인다. 소리 설정과 무관하게 작동한다.”라고 한다. 요청 기능과 동일한 조건이므로 새 후보가 없는 것은 두 출력 모두 타당하다. 그러나 A의 `$.cases[3].outputs.A.raw_output.no_candidate_reasons[0]`에서 말하는 잔여 불편 없음은 기능 일치 이상의 경험 결론이다. 기존 표시를 사용자가 보았는지, 그 결과 소리를 못 듣는 불편이 해소됐는지 기록이 없다. 정확한 기능 지원 확인으로 한정하면 유효하여 A 전체를 실패로 단정하지 않았다. B는 이 점을 가시성/인지의 가능성 질문으로 남긴다. 다만 사용자가 표시를 모른다는 질문 전제도 확인된 사실은 아니다. B의 completed는 알려진 지원 사양 검토 완료로 읽고 추가 질문은 탐색으로 취급했다.

HOLD-03의 “다른 모델의 설명서9.0: 상단 분사 강도는 약·중·강 세 단계로 선택할 수 있다.”는 대상 모델 1.0의 기능 근거가 될 수 없다. A는 이를 명시적으로 배제하고 보류한다. B의 `$.cases[0].outputs.B.raw_error.errors[0].details.violations`는 이 범위 불일치와 부합하지만, `raw_output=null` 및 `decision=null`이다. 올바른 오류 거절은 실질 욕구 추출·근거 비교·질문 제시 품질의 관측을 대신하지 않는다. 이 사례 B는 품질 100%나 완전한 의미 통과가 아니다.

HOLD-04의 두 리뷰는 같은 표준 각얼음 설정·같은 수량에서 각각 “출구에 매번 걸려 손으로 빼야 했다.”와 “출구에 한번도 걸리지 않고 모두 나왔다.”라고 한다. 양쪽 경험이 모순되므로 조건과 기기 차이를 확인해야 한다. 설명서의 “표준 각얼음 설정을 선택하면 각얼음이 배출구로 나온다.”는 걸림 방지나 자동 제거 구조의 부재를 뜻하지 않는다. B의 `$.cases[1].outputs.B.raw_output.gaps[0].remaining_pain` 및 두 `concept_assessments[*].reason`는 미언급을 부재로 확정한다. B의 원인·빈도 질문과 보편성 unresolved가 남아 있는데 completed인 것도 결론의 필수 조건을 미확인으로 둔 상태다. 자동 제거와 형상 개선 자체는 검토 가능한 가설이지만, 기존 기능 부재나 적용 원인을 입증한 후보는 아니다. A가 보류하면서 얼음 양을 추가 조건 예시로 든 것은 정확한 수량 조사로 읽을 수 있지만 이미 같은 수량이었다는 자료를 무시하는 원인 확정에 쓰면 안 된다.

HOLD-05에는 “다른 방에서 남은 세척 시간을 화면으로 확인할 수 있는지 알고 싶지만 설명서를 찾을 수 없다.”라는 리뷰만 있고 기능 자료는 없다. 기능 없음으로 결론내릴 수 없으며 A와 B 모두 이 사실은 유지한다. A의 `$.cases[5].outputs.A.raw_output.status`는 completed이지만 본문은 원격 기능 유무/사용 방법이 불명확하고 제품 검증 불가라고 인정한다. 핵심 검토 결론이 아직 없으므로 이 상태 불일치는 차단 결함이다. B의 held/unknown/질문은 이 정보 부족과 일치한다. B의 complaint 표시는 기능 미지원 사실이 아니라 정보 접근 불편을 뜻하는 것으로 읽었다.

HOLD-06은 이전 입력 스냅샷과 현재 자료를 직접 비교했다. 1.0은 “사용자가 가열 시간과 출력을 직접 설정한다. 음식의 가열 상태는 문을 열어 확인한다.”이고, 2.0은 “가열 센서가 목표 온도에 도달하면 문을 열지 않아도 외부 화면에 준비 완료 상태가 표시된다.”이다. 현재 버전은 센서 목표 도달의 외부 확인을 명시한다. A는 이 변경을 적용하여 후보를 만들지 않지만, `$.cases[4].outputs.A.raw_output.no_candidate_reasons[0]`의 “확인된 불편이 모두 해결”은 목표 온도가 사용자에게 충분한 가열과 같은 조건이라는 확인 없이 강하게 닫힌다. 그 조건이 같다면 후보 없음은 타당하므로 uncertain이다. B의 `desired_outcomes[0]`은 충분한 가열 확인을 실시간 진행 확인으로 바꾸고, `gaps[0].remaining_pain`도 미언급된 실시간 확인 기능으로 바꾼다. 시각 관찰과 설정 시간 대비 퍼센트가 음식이 충분히 데워졌는지 입증한다는 연결 근거는 없다. 추가 욕구 가설을 먼저 확인해야 한다. 이전 실제 출력이 없으므로 실제 수정 성공이나 이전 실행 결과는 판단하지 않았다.

측정 지표는 원래 scorecard의 필드를 모두 채웠다. 모든 카드에서 다른 모델/버전 사실 전용 오류는 0건, 명시된 동일 조건 기존 기능의 재포장 후보는 0건이다. 총 7개 proposed 후보를 현재 명시된 기능과 개념별로 비교했다. 다른 설계 가설이 같은 불편을 겨냥한다는 이유만으로 중복이라고 세지 않았다. 이 0건은 신규성이 제품 전체에서 입증되었거나 기타 의미 오류가 없다는 뜻이 아니다. 설명서에 없는 기능의 실제 부재는 확정하지 않았다. 사람 편집 시간은 측정하지 않았으며 `modification_seconds=null`을 전부 유지했다.

인용 검사는 bare evidence ID를 세지 않고 원문 형태로 소스에 명시 귀속한 따옴표 출현을 개별 검사했다. 별도 quote 필드가 없는 계약 때문에 UI 이름에 붙인 따옴표와 원문 인용을 구분해야 했다. 모든 따옴표 출현 6개 중 5개는 UI/용어 표시로 제외 사유와 경로를 citation-audit.json에 보존했다. 원문 귀속 인용은 HOLD-06 A의 1개이고 정확 인용은 0개다. 이 출력의 “문을 열어 꺼내야 하는”은 원문의 “문을 열어 꺼내야 해”와 정확 부분 문자열 일치가 아니다. 의미상 유사한 요약임은 인정하며 이 문구 차이만으로 의미 실패를 선언하지 않았다. 연관 해결 주장도 목표 온도 적용 조건이 미확인이다. 나머지 카드의 checked=0/correct=0은 인용 미관측이며 정확도는 null이고 품질 통과를 뜻하지 않는다. 인용 수치는 전체 근거 충실도를 대체하지 않는다. 출력의 UI 이름 따옴표를 원문 인용으로 다르게 해석하는 평가자는 공개된 제외 목록에서 다시 집계할 수 있다.

필수 정보가 없어 기능 지원이나 상충 조건을 결정하지 못하면 held 또는 명시적 조건화가 필요하다. 반면 이미 확인된 기능의 선택적 후속 탐색 질문이나 proposed 설계의 제조/기술 검증 질문만으로 완료된 초안을 실패시키지는 않는다. 기존 기능 지원과 실제 사용자 불편 해소를 구분하고, 욕구·불편·긍정 경험·조건부 기능 문장을 각각 보존했다. proposed 설계의 기대 효과는 실험으로 입증된 효과가 아니다. 각 판정과 차단 결함, 관찰, 불확실성의 원문 인용 및 정확 JSON 경로는 findings.json의 12개 case_assessments에 있다.

원래 동결 목록의 파일 해시 10개가 모두 일치하고, 여섯 review 입력은 각 materials 입력과 일치한다. 별도로 제공된 output.schema.json의 SHA256은 여섯 사례의 output_contract_sha256과 추가 동결 파일에 모두 일치했다. 추가 동결 파일이 가리킨 원래 input-freeze.json의 해시도 유지됐다. 원래 빈 scorecard 및 모든 입력 바이트를 보존했다. 파일·입력 무결성은 모델 실행 사실이나 실행 과정의 검증을 뜻하지 않는다.

- 한 번의 고정 합성 자료 6사례와 이미 생성된 익명 출력 12개만 평가했다.
- 평가자는 AI 한 명이며 작성자와 같은 기반 모델을 공유한다. 독립된 평가 문맥은 인간 독립성이나 보편적 심판 신뢰성을 보장하지 않는다.
- 블라인딩은 방법 라벨에만 적용됐다. 출력 구조, 오류 양식 및 문체가 방법을 드러낼 수 있고 라벨 대응은 사례별로 다를 수 있다. 방법 정체를 추정하지 않았다.
- 원본 합성 자료 및 동결 출력만 의미 평가했다. 실제 고객 효용, 제품 안전성, 모델 실행 진위/과정, 코드 품질, 인간 편집 소요 시간 또는 통계적 유의성은 평가하지 않았다.
- 사양 변경 사례의 이전 입력 스냅샷은 제공되었지만 이전 실제 모델 출력은 제공되지 않았다. 지원 근거 변화만 비교하며 실제 재생성/수정 성공은 주장하지 않는다.
- 짧은 설명서와 리뷰는 모든 제품 기능·사용 조건·실제 경험 해소를 증명하지 않는다. 기능 신규성 또는 효과의 미관측은 0건 지표의 품질 보증으로 바뀌지 않는다.
- 추가 제공된 동일 출력 계약은 원래 동결 해시와 사례별 계약 해시가 일치했다. 계약은 구조와 enum만 제공하며 지원/완료의 상세 의미를 정의하지 않아 의미 해석은 이 보고서의 일관된 정의에 따른다.
- PM 수용 또는 공식 평가 완료의 근거가 없다. independent_ai_assessment_complete=true는 이번 제한된 독립 AI 평가 작성의 완료만 뜻한다.

이번 독립 AI 의미 평가의 산출물 작성은 완료했다. `independent_ai_assessment_complete=true`, `formal_evaluation_complete=false`, `pm_acceptance=false`다. 모델 순위, 통계적 유의성, 실제 고객 효용, 제품 안전성 또는 PM Done 결론을 내리지 않는다. 평가를 위해 모델·생산 코드·테스트를 실행하거나 캡슐 밖 파일·Git·네트워크를 읽거나 외부 게시하지 않았다.
