# 검수기 입력 양식

이 양식은 인계받은 파일을 비교하기 위한 **별도 audit wrapper**다. 실제 Review/Evidence/API 계약을 변경하지 않는다. 임의 예측·원문·운영 응답을 채우면 안 된다.

`consumer-audit.py`에 manifest 파일을 전달하면 manifest와 같은 폴더 아래의 고정 파일만 읽는다. HTTP/등록/재시작/모델/OCR 호출은 없다. 파일 비교 결과는 지정한 새 출력 폴더에 쓴다.

## 최상위 필드

- `audit_input_format`: `data13-r5-consumer-v1`.
- `producer_commit`, `consumer_commit`: 실제 고정 40자리 Git SHA.
- `dataset_version`: 승인/후보 구분을 별도 증빙한 팩 버전 문자열.
- `files`: `{path, sha256}` 목록. 아래 참조되는 모든 파일을 포함한다. path는 manifest 폴더 아래 상대 경로여야 한다.
- `documents`: 문서별 대조 항목 목록.
- `captures`: 개별 evidence/scoped search 원 JSON의 전/후 캡처 목록.
- `restart_receipt_file`: files에 포함된 실제 재시작·동일 DB 범위 수신증 파일.
- `operating_origin_proof`, `pm_approval_proof`: 관련 원 증거의 위치. verifier의 내용 일치는 이 증거의 진위/승인을 자동으로 증명하지 않는다.

## documents의 항목

- `document_id`, `kind`(`review_csv` 또는 `pdf`), `source_file`.
- `expected_dataset_ref`, `expected_origins_ref`: `{file,pointer}`. pointer는 RFC6901 JSON pointer이며 빈 문자열은 root다.
- `stored_before_ref`, `stored_after_ref`: 같은 형식의 DB-export record 위치. SQL record가 JSON 문자열이면 `decode_json_string:true`도 명시한다.
- `metadata_before_ref`, `metadata_after_ref`: 같은 형식의 GET 원 응답 위치. 값은 기존 `{ok:true,data:record}` 응답이어야 한다.
- `original_before_file`, `original_after_file`: 원본 GET의 raw CSV/PDF 파일.
- `metadata_before_request`, `metadata_after_request`, `original_before_request`, `original_after_request`: method/path/params. 네 `_http_status` 필드도 같은 접미사 위치로 명시한다(예: `metadata_before_http_status`). 인계된 요청은 모두 해당 문서의 GET/200이어야 한다.

원본 CSV는 현재8열의 원행과 expected Review/Evidence ID·모델·판본·source_id·원문을 연결한다. PDF는 원본 bytes를 읽고 실제 pypdf native 페이지/문자 범위와 expected origins를 대조한다. PDF layout/OCR 정확도·SKU 기능 적용 판단은 이 검수 범위가 아니다.

## captures의 항목

- `id`, `phase`(`before`/`after`), `kind`(`evidence`/`search`).
- `request`: `{method:"GET", path, params}`. auth header나 비밀 값은 포함하지 않는다.
- `http_status`, `server_profile`(`documents` 또는 `public_api`).
- `response_ref`: files의 원 JSON 위치 `{file,pointer}`. 캡처 wrapper 안에 response가 있으면 해당 pointer를 지정한다.
- evidence: `expected_evidence_id`.
- search: `case_id`, `expect`(`success` 또는 `error`), 오류 사례는 `expected_error_code`.

필수 search case_id는 `selected-model`, `other-valid-model`, `invalid-model`, `invalid-version`이다. 각 사례를 before/after로 제공한다. 성공의 params는 model_id/document_version/q를 명시한다. 검색 item은 현재 `GroundedDocumentStore.search_evidence`의 shape로 제공한다.

## 결과 의미

- `MATCH`: 제공된 고정 파일·DB export·응답 내용 및 필수 쌍이 일치.
- `MISMATCH`: bytes/ID/scope/문자/shape 또는 기대 오류가 불일치.
- `UNCONFIRMED`: 인계·commit/version·필수 캡처/수신증이 없거나 필요한 확인 자료가 부족.
- exit code는 각각0/1/2. 실제 운영 출처·PM 인수는 별도 검수해야 하며 이 비교기는 `operating_origin_verified`와 `pm_approval_verified`를 false로 유지한다.
- 고정 contract source는 `8b41fd4785bc149593f04d913ef974f29fb341fe`다. 새 소비 commit의 계약 호환성도 별도 source 대조 대상이고 `consumer_contract_compatibility_verified=false`로 남긴다. 제공된 JSON 내용의 일치를 새 운영 코드의 호환성 승인으로 확대하지 않는다.

CLI 예시(경로만 제시하며 실제 캡처 예측은 포함하지 않음):

```text
python consumer-audit.py --packet <received-manifest.json> --output <new-audit-result-folder>
```
