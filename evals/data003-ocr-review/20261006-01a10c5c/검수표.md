### 각주 번호 혼입의 원인

OCR-MW-TABLE-05 원문은 `1000 W*1`, 저장 OCR은 `1000 W∗1`이다. 본값은 1000 W이고 1은 원문에 있는 각주 번호다. 원문과 저장 문자열 모두 일반 숫자 검색으로 [1000, 1]이 되므로 OCR이 새 숫자 1을 만든 것으로 판단하지 않는다. 기존 ledger의 observed_values=[1000.0,1.0], strict_numeric_field_correct=false는 그대로 보존했다. **기존 평가/필드 처리에서 본값과 각주를 분리할 필요가 있는 확인된 문제**다. 코드·gold·원 성적 10/11은 변경하지 않았다.

DATA003-MW23FDI-M06 현재 인용에는 Max.와 각주 본문이 보존되어 있다. M07은 정격 소비전력 1570 W를 인용한다. DUE D03 인용은 두 열의 치수·조건을 담지만 무게 행 이전에 끝난다. 같은 페이지 ID만으로 45 kg 등 모든 값의 인용 동등성을 주장하지 않는다. JSON은 같은 페이지 ID와 실제 구절 포함 ID를 분리하며, 구절 포함도 자동 열 연결의 성공으로 사용하지 않는다.

## 실행·검사와 남은 일

- 기존 제품 모델/OCR 70회 원결과를 읽기 전용으로 재사용. 추가 제품 모델/OCR 실행 없음.
- 원본 PDF 3개를 ledger의 SHA256과 대조했고 byte 동일 사본을 inputs에 보존.
- Poppler pdfinfo/pdftoppm 26.07.0으로 원본의 9개 페이지(표지 3, 대상 본문 6)와 표 상세 3개를 렌더링하여 시각 검수.
- 첫 렌더링 후 pdftotext.exe 호출은 설치 경로에 파일이 없어 exit 1. 모델/OCR 시도는 없었고 생성된 첫 PNG를 보존.
- 대체 텍스트 확인은 사전 설치된 bundled Python의 pypdf 6.10.0으로 PDF 문자층만 읽음. PDF 문자층 추출은 OCR이 아니며 레이아웃 정답으로 사용하지 않음.
- 새 검수용 표준 라이브러리 집계 스크립트만 -I -S -B -X utf8로 실행. 저장소 코드/테스트 import, 패키지 설치, 모델/OCR 재실행, 서버/자동화/예약 변경 없음.
- 첫 집계 실행은 표지 문서 버전의 문자층 일치 확인에서 실패(exit 1). 세 표지는 pypdf 문자층 추출이 깨지며 버전 문자열이 검색되지 않음. 3개 표지 렌더링에서 문서 번호·개정을 직접 확인한 관찰을 사용하고 문자층 한계를 별도 기록. 본문 14영역의 원문 구절은 문자층에서도 모두 대조됨.
- 첫 집계 스크립트 파일 생성 시 도구 JavaScript 문자열 구문 오류로 실행 전 실패. 그 시도는 파일/자료를 변경하거나 모델/OCR을 실행하지 않았으며 새 집계 스크립트 작성으로 복구.

집계 일관성 195항목 전부 일치. 저장 파일·해시·문자·시도 수·원문 구절·검수표 연결 확인이며 저장소 회귀 검사나 새 모델/OCR 성능 측정이 아니다.

자동 표의 실제 저장 출력과 모델/헤더/물리량/각주 연결 검사가 남았다. 같은 70회 OCR의 반복 실행을 제안하지 않았다. 기존 전체 표 출력이 있다면 이 표의 미확인 항목을 후속 검수할 수 있다. 냉장고 유형-SKU 연결과 C01 출처 상충은 미해결이다. #13 실제 handoff·새 corpus 검색 비교·PM 인수 등 #14의 다른 요구도 완료로 표시하지 않는다.
