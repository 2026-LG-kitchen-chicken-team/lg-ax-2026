## 2. 발견 사항(PM 보조 WEB AI에게 인계, 웹 미편집)

- **F1 회차별 검사 결과의 코드에 설명이 붙지 않음**
  - 위치: 화면 `JudgementViews.tsx`의 `CheckRounds`(`round.codes.join(', ')`), Markdown `planning.ts`의 회차 줄.
  - 증상: 회차 줄에 `INVALID_SEMANTIC_REVIEW`, `CONCEPT_GROUNDING_MISSING`, `NO_CANDIDATE_VIOLATION`, `NO_CANDIDATE_UNCERTAIN`이 코드만 나옵니다. 네 코드 모두 웹 설명 registry(`VIOLATION_LABELS`)에는 있습니다.
  - 재현: `web/fridge-normal.observed.json`의 `check_rounds`, `fridge-changed`·`fridge-missing-manual`도 같습니다.
  - 제안: 회차 코드에 `reasonText`를 적용합니다. 정보만 덧붙이는 변경이며, 판정은 바꾸지 않습니다.

## 3. 독립 시나리오(R5 수정 PR/운영 release 인계 뒤 실행)

모든 시나리오는 하나의 **입력·자료 버전(dataset_version + sha)·제품/문서 버전·모델 digest·코드 commit**을 기록하고, 화면·JSON·Markdown·MCP를 같은 실행 ID로 대조합니다.

| ID | 흐름 | 화면에서 확인할 것 | 실패로 볼 것 |
|---|---|---|---|
| S1 정상 새 요청 | 새 프로젝트 → 요청 → 실행 중 → 결과 | 실행 중 표시가 완성 후보로 보이지 않음. 결과가 accept일 때만 후보를 선택할 수 있음. 호출·토큰·내부 수정·검증 범위 표시 | 보류·실패인데 후보 선택 가능, 진행 중 결과를 완료로 표시 |
| S2 후보 선택 | accept 후보의 유지/집중/제외 → 저장 | 선택이 같은 실행 ID에 연결됨. 원문 근거 ID·문서 버전 표시 | 다른 실행·다른 자료 버전의 근거가 섞임 |
| S3 조건 변경 | 제외 조건·과제 변경 → 재실행 | 요청 회차 +1, 원 요청 대비 변경표(원 요청 열 정상 폭), 수정 전후·이력 연결. 내부 수정 회차와 구분 | 이전 후보를 새 결과로 상속, 회차 혼동 |
| S4 근거 부족 보류 | 설명서 없는 범위 요청 | 보류 사유·확인 질문·미해결(missing_information) 원문 그대로, 후보 없음 | 질문 없는 보류(PM 반례), 이미 있는 Need를 누락이라고 표시 |
| S5 판단 실패 | 수정 2회 소진 | 실패 표시, 회차별 위반 반복, 오류 세부(공개 코드·리뷰 ID·상충 경로) | 실패를 '생성된 후보 없음'으로만 표시, 성공 스타일 |
| S6 연결 오류 | 작업실/모델 서버 중단·타임아웃 | 연결 오류와 판단 실패를 구분, 다음 행동 안내, 저장 안 됨 | 오류를 빈 결과·보류로 표시 |
| S7 실제 후기 자료 | R5 실제 후기 자료팩 범위 | 실제/합성 구분, **SKU·작성일 미상과 격리 후기를 숨기지 않음**, 원문·출처·후기 ID·수집일 | 미상을 추정값으로 채움, 불편 후기만 골라 표시 |
| S8 자료 버전 변경 | 자료팩 버전이 바뀐 뒤 기존 프로젝트 열기 | 기존 프로젝트를 새 범위로 재사용하지 않음, 버전 불일치 안내 | 다른 버전 근거로 이어서 실행 |
| S9 내보내기·MCP | S1~S5 각각 | JSON·Markdown의 실행 ID·상태·토큰·오류·근거 원문 SHA와 MCP 응답이 같음 | 내보내기 누락·불일치 |

- 구분 기록: 초기 파일럿(제품군별 1모델) / 전체 18모델 / 원 응답 재조회 / 새 모델 실행 / 팀 내부 시험 / 실제 사용자 리뷰 수집 / 최종 제출.

## 4. 첫 내부 사용자 테스트 체크리스트(파일럿 새 요청)

1. 시작 조건: 코드 commit, 운영 release, 자료팩 버전/sha, 모델 digest, 시험자(팀 내부)와 시각을 기록합니다.
2. 과제를 줍니다. 예: "선반 청소 불편을 줄이는 개선안을 요청하고, 결과 근거를 원문까지 확인한 뒤 회의용으로 내보내라."
3. 관찰합니다(시간 측정 포함). 요청 입력, 실행 중 대기 이해, 결과 상태(성공/보류/실패) 이해, 원문 근거 찾기, 조건 변경, 내보내기를 봅니다.
4. 질문합니다. "이 결과는 채택된 후보인가?", "왜 보류인가?", "이 근거는 실제 후기인가 합성인가?", "모델 사용량은 얼마인가?"
5. 기록합니다. 막힌 지점, 오해한 표시, 걸린 시간, 화면 캡처를 남깁니다. 실제 사용자 효용 증거가 아니라 **팀 내부 시험**으로 표시합니다.

## 5. 발표·영상·ZIP 표시 점검

- 모든 화면 캡처에 실행 ID·코드 commit·자료 버전·모델이 보이게 합니다. 성공/보류/실패를 실제 결과대로 표시합니다.
- 합성자료와 실제 후기를 구분하고, 정상 accepted run이 없으면 '정상 완료'를 시연하지 않습니다.
