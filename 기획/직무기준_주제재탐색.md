# 직무와 작업 결과를 기준으로 한 주제 재탐색

2026-09-27 · 최신 요청: Theme A/B에서 누구의 어떤 업무를 어디까지 수행하는 Agent인지 먼저 정하고 다시 탐색·도출한다.

**Theme A에서는 ‘생활 방식·가구 특성 기반 가전 폼팩터 기획 Agent’, Theme B에서는 ‘키친 가전 연계 서비스 설계·검증 Agent’를 우선 후보로 도출했다.** 주제명을 포괄적으로 바꾸는 데서 그치지 않고 업무의 시작·끝, 재실행 조건, 검토 가능한 산출물을 다시 정의했다. 현재는 탐색 후 추천이며 단일 출품 주제 확정이나 Agent 구현 완료가 아니다.

## 1. 탐색 단위와 공식 해석

공식 선택 단위는 Theme A/B다. 표의 ‘포함 가능 과제’는 활용할 방향이며, 표의 한 행만 선택하거나 여섯 행을 전부 구현하라는 요구는 확인되지 않았다. 여러 항목을 연결할 수 있다는 것은 공고 표현과 추가 주제 자료를 종합한 해석이다. 운영기관의 별도 답변을 받은 사실은 없다.

공식 추가 자료 19~20쪽은 A의 상품기획 업무와 B의 UX/UI 시나리오 설계 업무를 반복하는 Agent를 요구한다. 28쪽은 역할을 예시로 설명하며 누구의 수고를 덜지 먼저 정하도록 한다. 따라서 이번 후보는 ‘직무 전체 자동화’라는 무제한 목표가 아니라, **직무 안에서 자료를 받아 검토 가능한 결과를 넘겨주는 하나의 완결된 업무**다.

| 구분 | Theme A | Theme B |
|---|---|---|
| 직접 사용자 | 키친 가전 상품기획자·선행기획 담당자 | 키친 서비스 기획자·UX/UI 시나리오 설계자 |
| 핵심 질문 | 어떤 제품·기능·구조를 왜 기획할 것인가? | 그 제품·기능을 고객이 어떤 과정으로 쓰게 할 것인가? |
| 업무의 끝 | 근거·대안·미확인이 명시된 콘셉트와 요구사항 | 시나리오·사람/가전 역할·화면·예외 흐름·검사 기록 |
| 재실행 계기 | 새 고객 요구·기술·경쟁 제품·제약 조건 | 고객 상황·기능·역할·목표·상태 조건의 변경 |
| 사람에게 남는 판단 | 제품 전략, 제조 가능성, 최종 채택 | 고객 경험의 가치, 사용성, 실제 서비스 적용 |

## 2. 이번 조사에서 달라진 판단

- **기획 업무의 존재와 우리 도구의 수요를 구분한다.** LG는 고객 조사와 엔지니어·디자이너의 연결을 설명하고 있다. Dovetail의 Breville 사례도 가전 기획·UX에서 고객 근거를 공유하는 업무를 보여준다. 공급자 및 제조사 자료이므로 우리 Agent의 구매 의향이나 시간 절감 효과까지 입증하지 않는다.
- **출처를 붙인 리뷰 분석만으로는 차별화가 약하다.** Dovetail은 고객 근거에 기반한 Agent와 반복 작업을 이미 제공한다. ‘Agent’, ‘출처’, ‘반복’이라는 표현 자체를 신규성으로 내세우지 않는다.
- **화면 생성만으로는 차별화가 약하다.** Figma Make 공식 안내는 대화로 작동하는 프로토타입과 웹 UI를 만들고 수정하는 기능을 설명한다. 우리 B 후보는 가전·사람·상태 제약과 UX 산출물 사이의 일관성 검사에서 추가 가치를 검증해야 한다.
- **서비스 흐름 설계는 실제 업무다.** NN/g의 97명 실무자 조사와 서비스 설계 자료는 고객 행동과 사람·시스템·과정의 관계를 검토하는 업무를 보여준다. 표본은 여러 산업이며 LG 키친에 대한 조사나 우리 제품 수요 조사가 아니다. 제어할 수 있는 작은 경험부터 범위를 정하라는 방법론도 구현 범위를 정하는 참고로 사용했다.

## 3. 새로 비교한 여섯 업무형 후보

이 이름은 공식 과제 번호가 아니다. 과거 A1/B1 등과 혼동하지 않도록 내부 ID는 ROLE_로 구분한다. 모든 소비자 사례는 설계용 예시이며 현업 인터뷰·실수요 검증 결과가 아니다.

### A-기회: 고객 근거를 제품 개선 기획으로 연결하는 Agent

- **사용자·수고:** 상품기획자가 흩어진 고객 의견을 묶고 기존 기능으로 해결되는지 확인한 뒤 개선 과제를 작성하는 일.
- **입력:** 사용 권한이 있는 고객 조사/리뷰 원문, 제품·경쟁 기능 자료, 목표 고객군.
- **과정:** 의견 정리→요구 가설→기존 기능·반례 조회→남는 문제 판별→기능/서비스 콘셉트→근거 누락·중복 검사→수정.
- **결과:** 개선 기회 카드, 원문 연결표, 기존 대안과의 차이, 요구사항, 추가 조사 질문.
- **키친 콘셉트 예시:** 준비·조리·세척 사이에서 반복되는 분해/정리 작업을 줄이는 구조 또는 관리 기능. 특정 가전을 미리 확정하지 않는다.
- **반복 사용:** 새 자료 묶음이나 새 제품이 들어오면 기존 기회가 여전히 남는지 다시 검토.
- **구현 경계:** 한 제품군과 검토된 원문 30개 내외부터 시작할 계획. 아직 그 원문을 확보하지 않았다. 합성 리뷰를 수요 근거로 사용하지 않는다.
- **판단:** 업무는 분명하고 구현은 중간 난도지만 원문 확보와 Dovetail·강한 리서치 프롬프트 대비 가치가 약점. A의 차선 후보.

### A-형태: 생활 방식·가구 특성 기반 가전 폼팩터 기획 Agent

- **사용자·수고:** 상품기획자가 다른 고객군의 요구를 제품 형태·구조 조건으로 번역하고 대안을 비교하는 일.
- **입력:** 기획 브리프, 출처가 있는 고객 요구, 기존 제품 명세·기능, 우선순위와 필수 제약.
- **과정:** 요구 구조화→기존 대안·관련 기술 조회→충족/미충족 구분→형태/구조 후보→검증 가능한 수치·기능 조건 검사→충돌 수정 또는 미확인 보류.
- **결과:** 콘셉트 후보 카드 2~3개, 요구-근거-기능 연결표, 상충 조건 비교, 검토용 스케치, 미확인 기술 과제. 제조 도면이나 설치 승인서가 아니다.
- **키친 콘셉트 예시:** 작은 공간, 많은 저장량, 접근 방식 등 서로 다른 요구에 대응하는 크기·수납 구획·개폐 방식·배치 구성. 작은 주방은 첫 사례이며 전체 Agent의 한계가 아니다.
- **반복 사용:** 같은 제품군에서 고객 요구와 우선순위를 바꿨을 때 대안·탈락 이유·추가 자료 요청이 달라져야 한다.
- **구현 경계:** 한 제품군, 검토된 모델 5개 내외, 검증할 조건 3~4종, 서로 다른 브리프 2개부터 시작할 계획. 인체공학·모듈 강도·이동성은 자료 없이 자동 검증했다고 하지 않는다.
- **판단:** 제품 형태 선택이라는 결정과 결과물이 뚜렷하다. A의 우선 후보. 수치 대조 외의 요구 해석·콘셉트 품질과 제조 타당성은 별도 위험이다.

### A-기술: 고객 문제에서 출발하는 타산업 기술 적용 기획 Agent

- **사용자·수고:** 선행 상품기획자가 특정 고객 문제를 해결할 기술을 찾고 적용 조건·한계를 정리하는 일.
- **입력:** 고객 문제, 크기/비용/환경 등 목표 조건, 논문·특허·기술 자료.
- **과정:** 문제를 기능 요구로 변환→타산업 기술 검색→원문 조건 추출→가정용 환경과 비교→적용 구조/서비스 제안→상충 근거와 추가 실험 계획.
- **결과:** 기술-요구 매핑, 후보 비교, 적용 콘셉트, 미확인 항목과 실험 제안.
- **키친 콘셉트 예시:** 보관 환경이나 준비·관리 부담을 줄이는 기술을 다른 산업에서 가져와 가정용 모듈/기능에 적용.
- **반복 사용:** 다른 문제 또는 신규 문헌이 들어오면 후보·근거·검증 계획을 갱신.
- **구현 경계:** 기술군 하나와 검토된 문헌 묶음. 신규성·특허 권리·성능 향상을 자동 보증하지 않는다.
- **판단:** 공식 A 업무에 맞지만 원문 해석과 적용 타당성의 평가가 어렵다. 자료 검색 코드보다 전문 검증 부담이 커 후순위.

### B-연계: 키친 가전 연계 서비스 설계·검증 Agent

- **사용자·수고:** UX 설계자가 고객 요구를 사람·가전·앱의 역할로 나누고, 정상/변경/실패 상황의 서비스 흐름과 화면을 일관되게 만드는 일.
- **입력:** 고객 목표·상황, 검토된 가전 기능 명세, 사람 작업, 사용자 확인 정책, 시간/자원 조건.
- **과정:** 누락 질문→서비스 대안 구성→사용자/기기 흐름 구조화→지원 기능·선행 관계·자원·상태 검사→오류 근거로 수정→UX 흐름·화면·검사 사례 생성→조건 변경 후 재검사.
- **결과:** 서비스 콘셉트, 사용자 여정과 기기/사람 역할표, 정상·예외 흐름, 화면 3~5개, 제약 검사와 수정 이력, 개발 인계용 요구사항.
- **키친 콘셉트 예시:** 하나의 식사 준비 계획을 여러 가전과 사람이 공유하고, 지연·취소·가전 사용 불가 때 남은 안내와 선택지를 일관되게 바꾸는 연결 주방 경험.
- **반복 사용:** 가전 조합·사람 수·목표·지원 기능이 바뀌면 새 흐름과 화면을 다시 설계. 동일 입력에 정해진 이야기만 재생하면 부족하다.
- **구현 경계:** 첫 구현은 가전 2종, 작업자 1명, 한 시나리오 6~8작업, 검토된 작업 자료와 고정 화면 요소. 한 끼 경험으로 검증하되 Agent의 주제를 조리 시간 계산 하나로 한정하지 않는다. 새로운 제품 기능은 현재 지원 기능과 분리해 표시한다.
- **판단:** B의 우선 후보. 제약 계산과 상태 검사로 잘못된 설계를 설명할 수 있다. 개발팀으로 넘길 UX 산출물의 품질과 실제 재사용 효과는 아직 검증이 필요하다.

### B-개인화: 가구별 조리 서비스 정책·예외 흐름 설계 Agent

- **사용자·수고:** 서비스 기획자가 가족별 취향·시간·분량 조건의 조합을 정책과 화면 분기로 만드는 일.
- **입력:** 가구별 요구, 지원할 요리/기능, 충돌 시 우선순위와 추가 확인 정책.
- **과정:** 조건 구분→공통 과정/개인별 선택 설계→불가능 조합 탐색→질문·선택·대안 흐름→화면·테스트 표 생성→정책 변경 재검사.
- **결과:** 개인화 정책표, 공동/개별 조리 흐름, 충돌 설명 화면, 조합별 검사 사례.
- **키친 콘셉트 예시:** 가족의 공통 조리 과정과 개인 옵션을 나누고, 모두의 조건을 동시에 만족하지 못하면 선택을 요청하는 식사 서비스.
- **반복 사용:** 가구 조건과 지원 메뉴가 바뀔 때 정책 충돌과 화면을 함께 수정.
- **구현 경계:** 취향·시간·분량 등 비의료 조건, 검토된 요리 소수. 치료 식단·알레르기 안전 판단은 포함하지 않는다.
- **판단:** 데이터와 규칙을 좁히면 구현 가능하지만 기존 개인화 서비스와의 차별성, 기획자 전용 도구의 필요성이 약하다. B의 차선 후보.

### B-공동사용: 가족의 작업 인계·공동사용 경험 설계 Agent

- **사용자·수고:** UX 설계자가 가족 중 누가 준비·확인·마무리를 맡는지, 변경 시 어떤 알림과 확인이 필요한지 설계하는 일.
- **입력:** 구성원 역할, 기기/앱 기능, 공동 작업, 책임 변경·취소·통신 불가 정책.
- **과정:** 역할·상태 모델→업무 인계 경로→중복 실행·미확인 인계 검사→확인/대기/복구 UX→역할 변경 테스트.
- **결과:** 역할·상태별 서비스 흐름, 작업 인계 화면, 누락·중복 방지 정책, 검사 사례.
- **키친 콘셉트 예시:** 한 사람이 식재료를 준비하고 다른 사람이 조리·정리를 이어받을 때 완료/인계 상태를 공유하는 경험.
- **반복 사용:** 동거·가족 구성이나 작업 담당자가 달라져도 같은 설계 과정을 수행.
- **구현 경계:** 가상 역할 2개와 작업 1종. 실제 계정 권한·기기 제어는 별도 명세를 확인해야 한다.
- **판단:** 협업 경험이 구체적이나 현재 확보한 가족 공동사용 수요와 권한 자료가 적다. 가전 제어 UI만 만들면 일반 업무 인계 도구와 겹친다.

## 4. 비교와 도출 결과

공식 배점·합격 확률이 아닌 내부 설계 판단이다. 사용 가치는 업무 존재를 바탕으로 한 가설이며 우리 Agent의 채택은 미확인이다. 난도는 제한된 시연용 Agent에 자료 정리·검사·실패 처리까지 포함했다.

| 후보 | 직접 사용자에게 넘길 핵심 결과 | 서류 설득력 | MVP 난도 | 반복 업무 가치 | 가장 큰 위험 | 결론 |
|---|---|---|---|---|---|---|
| A-기회 | 근거로 반증한 개선 기회·요구사항 | 중 | 중 | 높음·가설 | 실제 원문 확보·기존 고객 분석 Agent 중복 | A 차선 |
| A-형태 | 생활 조건에 맞는 형태·구조 콘셉트 비교 | 중~높음 | 중~상 | 중~높음·가설 | 수요→형태의 타당성·물리 검증·추천표 수준에 머묾 | **A 우선** |
| A-기술 | 적용 콘셉트·한계·추가 실험 계획 | 중~높음 | 높음 | 중·가설 | 기술 조건 전용·전문가 평가 | 후순위 |
| B-연계 | 검사된 서비스 흐름·화면·예외·수정 이력 | 중~높음 | 중 | 중~높음·가설 | 원자료·상태 모델과 UX 산출물의 일관성 | **B 우선** |
| B-개인화 | 정책 충돌을 처리하는 개인화 흐름 | 중 | 중 | 중·가설 | 기존 맞춤 서비스 중복·요리 조건 타당성 | B 차선 |
| B-공동사용 | 인계·확인·복구 흐름과 화면 | 중 | 중 | 중·가설 | 구체적 수요·역할/기능 명세 부족 | 후순위 |

이전 평가의 ‘높음’ 표현을 그대로 승계하지 않았다. 업무 범위가 확장되어 요구 해석, 근거 연결, 새 결과물 품질이 추가됐기 때문이다. 현재 환경에서 **전체 검증 우선순위는 B-연계, 다음은 A-형태**로 판단한다. 이것은 최종 출품 테마의 확정이 아니다.

### A-형태를 우선한 이유

고객 분석 자체는 기존 도구와 많이 겹친다. 폼팩터 기획은 ‘무엇을 조사하나’에서 ‘어떤 형태 대안을 어떤 조건으로 비교하나’로 업무의 끝이 명확하다. 구현 가능한 부분은 수치·기능·출처 검사로 정하고, 검증할 수 없는 제조·인체공학 판단은 미확인으로 남길 수 있다. 다만 이 경계를 잘못 잡으면 기존 제품 추천 도구가 되므로 요구→새 콘셉트 연결을 평가해야 한다.

### B-연계를 우선한 이유

고객의 목표를 사람·가전·앱의 역할로 나누는 업무는 공식 B의 전체 흐름을 잘 보여준다. 지원하지 않는 동작, 순서 충돌, 지연, 미확인 상태를 이유와 함께 찾아 고치는 과정을 시연할 수 있다. 기존 계산·상태 검사 코드가 일부 재사용 가능하나, 기존 코드가 있다는 사실을 주된 선정 근거로 삼지는 않았다. 직접 생성되는 서비스 설계와 UX 결과물이 쓸 만한지 확인하는 것이 핵심이다.

## 5. 전체 주제·최소 구현·시연을 분리한다

| 구분 | A-형태 | B-연계 |
|---|---|---|
| 전체 업무 | 생활 요구를 제품 형태/구조 콘셉트로 변환·검토 | 고객 목표를 가전/사람의 연결 경험으로 설계·검사 |
| 첫 구현 | 한 제품군, 자료로 확인 가능한 조건 3~4종 | 가전 2종, 한 경험, 한정된 상태/화면 요소 |
| 첫 사례 | 작은 공간과 개폐/용량 요구 | 여러 메뉴의 식사 준비와 상태 변화 |
| 재사용 확인 | 저장량 등 다른 요구로 같은 작업 재실행 | 가전·사용자 작업·목표 변경으로 흐름 재생성 |
| 초기 범위 밖 | 전 가전 자동 설계, CAD·제조·인체공학 보증 | 전 주방 자동 운영, 실기기 제어, 임의 레시피 검증 |

제안서는 전체 업무와 범위를 설명하되, 시연 사례 하나를 전체 주제명으로 사용하지 않는다. 반대로 시연 하나만 구현하고 범용 Agent가 검증됐다고 하지 않는다.

## 6. 기존 12개의 활용

다음은 가능 기능의 매핑이며 전부 구현하겠다는 약속이 아니다. 각 후보의 업무에 필요한 부분만 선택한다.

| 기존 항목 | 새 탐색에서 활용할 위치 |
|---|---|
| A의 고객 니즈·라이프스타일 | 상품기획 입력과 요구 정리. A-기회/A-형태에 주로 활용 |
| A의 논문·특허·타산업 기술 | 콘셉트의 기술 근거 조사. A-기술에 핵심, 다른 후보에는 필요할 때 사용 |
| A의 영상·음향 인식 | 별도 검증이 필요한 관찰 도구 후보. 전체 Agent의 필수 기능 아님 |
| A의 니즈+기술 콘셉트 | 상품기획 결과물 |
| B의 Zero-Touch·가전 연계·미래 시나리오 | 연결 경험의 목표·서비스 흐름·대표 사례 |
| B의 개인화 | 고객 조건과 분기 정책 |
| B의 안전·지속가능성 | 근거를 확보한 범위의 확인/자원 조건. 안전 보증·절감 실측을 자동 주장하지 않음 |

## 7. 검증 상태와 다음 실험

**이번에 실제 수행:** 기존 공식 자료 재확인, 최신 직무·경쟁 도구의 1차 자료 조사, 서로 다른 6개 업무 후보 도출, 공통 비교, 상위 두 후보의 업무/산출물/범위 계약 재설계.

**과거 실험에서 재사용 가능한 증거:** A의 명세 2종·공간 조합 8개는 일부 수치 검사만, B의 합성 일정 6개와 상태 그래프 검사는 일부 실행/실패 처리만 다룬다. 이번 확장된 업무 전체의 검증 결과로 합산하거나 새 실험처럼 보고하지 않는다.

**아직 하지 않음:** 새 후보의 실제 모델 실행, 고객 조사 원문 확보, 현업 사용자 인터뷰, LLM/기존 도구와의 통제 비교, 제조 검토, 실제 가전 연동, 제안서·접수 완료.

다음 실험은 기능을 늘리기 전에 공통 입력을 준비하여 강한 LLM 직접 사용 / 수동 구조화+기존 도구 / Agent 방식을 비교한다. 준비·입력 정리 시간과 수동 수정도 비용에 포함한다.

| 후보 | 비교 입력과 변화 | 검토할 산출물 | 실패·중단 기준 |
|---|---|---|---|
| A-형태 | 같은 제품 자료에 서로 다른 생활 요구 2개, 치수 누락/상충 요구 추가 | 콘셉트와 요구 연결, 기존 대안 대조, 출처/단위, 불확실성 표시 | 새 요구에도 같은 추천표, 근거 없는 형태·성능, 현업이 검토할 가치가 없는 결과 |
| B-연계 | 같은 기능 명세에 정상/변경/취소/미확인 상태, 작업자·가전 조건 변경 | 흐름·화면·검사 결과의 일치, 불가능 처리, 재설계 이유 | 고정 시나리오 재생, 미지원 기능 발명, 상태와 다른 완료 화면, 도구를 붙여도 수정 수고 증가 |

기준선 품질이 충분하면 Agent 구조를 더 복잡하게 만들지 않는다. 새로운 가치를 입증하지 못하면 범위를 바꾸거나 해당 후보를 보류한다. 이 원칙은 추천을 무기한 미루기 위한 것이 아니라 구현 중 잘못된 방향을 빨리 발견하기 위한 기준이다.
