# 고객 불편·기존 제품 대조 기반 키친 상품기획 Agent

Theme A / 2026-09-27 사용자 채택 / 공식 양식용 원고

## 1. 아이디어 제안내용 개요

### 제안: 불편의 근거와 제품 기능을 연결하는 AI 상품기획 담당자
키친 상품기획자가 고객 리뷰와 제품 설명서를 함께 검토할 때, 무엇이 이미 해결된 문제이고 무엇이 여전히 남은 불편인지 구분하도록 돕는 Agent를 개발한다. 기획 요청과 자료를 입력하면 고객 불편을 구조화하고, 해당 모델의 기존 기능과 대조한 뒤, 근거가 연결된 신규 기능·제품·서비스 콘셉트와 요구사항을 작성한다.

### 입력 → 수행 → 산출물
입력은 대상 고객·제품군·기획 조건, 리뷰 CSV, 제품 명세·설명서다. Agent는 조사 계획 수립 → 관련 자료 조회 → 불편 묶기 → 모델별 기능 대조 → 기회 후보 생성 → 근거·중복 검사 → 수정 순서로 업무를 수행한다. 결과는 ① 원문이 연결된 불편 목록 ② 기존 기능과 잔여 불편의 대조표 ③ 콘셉트 2~3개와 요구사항 ④ 확인이 필요한 가정 ⑤ 실행·수정 기록이다.

### 첫 구현과 시연 범위
하나의 키친 가전 제품군에서 가상 모델 3~5개와 합성 리뷰 30~50개로 전체 흐름을 구현한다. 첫 시연은 냉장고의 수납·정리·청소 상황으로 구성하되, 제품군은 교체 가능한 입력으로 설계한다. PC의 웹 화면에서 Agent의 실제 분석·조회·검사·수정을 보여준다. 실기기 제어나 제조용 설계도, 물리 시뮬레이션은 초기 구현의 필수 범위로 두지 않는다.

## 2. 제안배경

### 고객의 말에서 신규 기획으로 넘어가는 대조 업무
리뷰에 “선반 청소가 어렵다”는 표현이 있어도, 곧바로 “분리형 선반을 만들자”는 결론을 낼 수는 없다. 해당 모델에 이미 분리 기능이 있을 수 있고, 같은 불편 표현이 탈착 방법을 모르는 문제와 식품을 모두 꺼내야 하는 구조적 부담을 함께 가리킬 수 있기 때문이다. 상품기획에는 불편 요약 이후에 모델·기능·사용 조건을 연결하는 검토가 필요하다. 이 예시는 업무 설명을 위한 가상 사례다.

### 관련 업무의 활용 사례와 남은 검증 과제
주방가전 기업 Breville의 공개 사례는 고객 연구를 제품·디자인 의사결정에 활용하고 연구 자료를 조직 내에서 공유하는 업무를 소개한다.[1] Dovetail은 고객 데이터의 근거 조회와 반복 업무를 수행하는 AI Agent 기능을 이미 제공한다.[2] 따라서 단순 리뷰 요약이나 문서 생성 자체를 신규성으로 주장하지 않는다. 본 제안은 키친 제품의 모델별 기능 대조와 미해결 불편의 구분을 하나의 검토 흐름으로 묶는 데 초점을 둔다. 실제 국내 기획자의 사용 빈도와 도입 효과는 후속 인터뷰·과제 평가로 확인한다.

### Theme A와의 연결
고객 리뷰에서 니즈를 찾고, 기존 제품 정보를 비교해 기회를 발굴하며, 그 근거로 키친 기능·제품·서비스 콘셉트를 제안한다. 공식 Theme A의 AI 상품기획 역할을 반복 수행하는 구현물로 구체화한다.[3] 사용자가 원하는 것은 특정 가전의 고정 답안이 아니라, 기획 조건과 자료가 바뀌어도 다시 실행할 수 있는 업무 도구다.

## 3. 활용정보

### A. 기획 요청과 분석 범위
사용자는 제품군, 목표 고객, 사용 상황, 우선 검토할 불편, 제외 조건을 입력한다. Agent는 누락된 조건을 질문하고 이번 실행에서 확인할 항목을 계획한다. 제품 가격·치수 등 수치 조건은 단위와 기준을 함께 기록한다. 입력하지 않은 조건을 사실처럼 만들어 채우지 않는다.

### B. 고객 불편 자료
리뷰 자료에는 review_id, product_id, 원문, 작성 시점, 출처, 합성 여부를 저장한다. 하나의 리뷰에서 불편·사용 조건·희망 결과를 구분하고 각 판단에 원문 구절을 연결한다. 같은 문장의 반복과 유사 표현을 묶되, 시연용 샘플의 빈도를 시장 수요 비율로 해석하지 않는다. 실자료를 추가할 때에는 사용 권한과 개인정보 포함 여부를 확인한다.

### C. 제품 기능 자료
제품별 모델 식별자, 문서 버전·적용 지역, 기능 설명, 사용 조건, 근거 위치를 저장한다. 초기에는 직접 작성한 가상 제품 명세와 문서 발췌로 통제된 검증 자료집을 구성한다. 이후 공개 제조사 자료를 대상으로 모델·문서의 연결 정확도를 추가 검증한다. 설명서에 표현이 없다는 이유만으로 해당 기능이 없다고 단정하지 않는다.

### D. 데이터의 성격을 화면과 결과물에 표시
각 자료에 ‘실제 공개 자료 / 합성 시연 자료’를 표시하고 모든 출력까지 이 구분을 유지한다. 합성 리뷰와 가상 명세는 시연·기능 검증용이며 실제 고객 니즈나 LG 제품의 사양을 입증하지 않는다. 자료집 버전과 실행 ID를 보관해 같은 입력의 결과를 다시 확인할 수 있게 한다. 외부 자동 수집이나 기업 내부 데이터 확보는 최초 시연의 선행 조건으로 두지 않는다.

## 4. 제안 아이디어 설명 및 차별성

### Agent가 수행하는 5개 Skill
① 자료 조회: 요청에 맞는 리뷰·제품 문서를 찾고 원문 ID와 위치를 반환한다.
② 니즈 구조화: 고객 상황, 불편, 희망 결과, 상충 의견을 묶는다.
③ 기능 대조: 동일 모델·버전의 기능과 사용 조건을 확인하고 ‘기존 대응 있음 / 잔여 불편 가설 / 근거 부족’으로 나눈다.
④ 콘셉트 작성: 남은 불편에 연결되는 후보 2~3개, 기능 요구사항, 예상 제약, 검증 질문을 작성한다.
⑤ 검토·수정: 인용 누락, 모델 혼동, 기존 기능 재제안, 근거를 넘는 단정을 검사하고 해당 단계로 되돌린다.

### 동작 예시: 냉장고 청소·정리 기획 요청
가상 리뷰 R-01은 “음료가 새면 선반 위 식품을 모두 꺼내야 해서 청소를 미룬다”는 상황을 담는다. 가상 제품 명세 P-01에는 ‘분리형 선반’이 이미 존재한다. Agent는 단순히 분리형 선반을 새 기능으로 제안하는 대신, ‘선반 분리 가능’과 ‘식품 이동 부담 감소’를 서로 다른 요구로 구분한다. 이후 ‘오염된 구획만 분리해 세척하는 수납 모듈’을 후보로 제안하고, 수납 손실·액체 유출 경로·식품 접촉 소재·세척성을 추가 검토 항목으로 남긴다. 이 콘셉트는 가상 사례의 설계 가설이며 제조 가능성이나 실제 수요를 확인한 결과가 아니다.

### 변경 입력에 따른 재검토
시연 도중 제품 명세에 ‘구획별 분리 수납함’이 이미 있다는 조건을 추가한다. Agent는 기존 제안이 겹치는지 다시 판단하고, 차이가 없으면 후보를 제외하거나 근거 부족으로 보류한다. 남는 차이가 있다면 어떤 사용 조건에서 무엇이 개선되는지를 원문과 함께 수정한다. 검증 가능한 기회가 없을 때에는 억지로 신제품을 만들지 않고 추가 조사 질문을 제시한다.

### 일반 LLM·기존 도구 대비 확인할 가치
일반 LLM도 좋은 프롬프트와 자료로 유사한 분석을 할 수 있다. 본 Agent의 가치는 모델의 독점 능력이 아니라, 자료·모델 ID를 연결하고 대조표의 각 판단을 검사하며 변경 후 영향을 다시 검토하는 일관된 실행 절차에 있다. 동일 자료를 제공한 강한 단일 프롬프트 기준선과 비교해 실제로 오류나 사람의 수정 부담을 줄이는지 평가한다. 기존 고객 분석 도구의 기능 부재나 자사 방식의 우월성을 사전 결론으로 두지 않는다.

## 5. 추진방향

### 구현 구조와 반복 실행
Python 기반 실행기, 구조화 출력을 지원하는 LLM 1개, CSV·문서 저장소, 간단한 웹 UI로 구성한다. LLM은 계획·의미 해석·기획·재검토를 맡고, 코드는 자료 조회·ID 확인·필수 항목 검사·결과 저장을 맡는다. 입력 규모를 제한해 복잡한 인프라 없이 시작한다. 모델 API는 선발 후 실제 호출·비용·응답 형식을 먼저 확인하고 교체 가능한 어댑터로 연결한다.

검사 실패 시 관련 자료를 다시 조회하고 최대 2회 수정한다. 이후에도 해결되지 않으면 불확실한 항목과 이유를 표시하고 종료한다. 원문에 포함된 지시문은 자료로만 취급하며 실행 명령으로 사용하지 않는다. 웹 화면은 요청 입력, 근거·대조표, 콘셉트 비교, 수정 이력으로 구성한다. 준비된 입력을 쓰더라도 결과 생성과 검사는 실행 시점에 실제로 수행한다.

### 일정과 3인 협업 계획
10/2~10/5: 입력 계약, 샘플 자료집, 조회→대조→콘셉트의 첫 실행을 완성한다.
10/6~10/8: LG 연구원 컨설팅에서 기획 산출물의 실무 적합성과 제품 대조 기준을 점검한다.
10/9~10/13: 오류 수정 루프와 웹 UI를 연결한다.
10/14~10/17: 독립 평가와 개선을 수행한다.
10/18~10/20: 실행물·제안서·재사용 안내·20쪽 이내 발표자료를 정리해 결과물을 제출한다. 10/28 본선에 대비해 5분 시연을 준비한다.[3]

팀장은 정이량이며, 3인은 Agent·도구 구현, 데이터·평가, UI·문서의 세 역할을 나눠 개발하고 교차 검토한다. 개인별 세부 개발 역할은 착수 시 확정한다.

### 검증 설계
정상 입력, 기존 기능 중복, 모델 혼동, 상충 리뷰, 근거 누락, 명세 변경을 포함한 독립 사례 12개를 개발 예시와 분리한다. 같은 모델·자료·출력 항목을 준 단일 프롬프트와 Agent를 각각 3회 실행한다. 원문 추적 가능 비율, 모델·기능 연결 오류, 근거 없는 단정, 기존 기능 재제안, 수정 시간, 실행 지연·비용을 기록한다. 사람 검토자는 방식 이름을 가린 결과를 동일 기준표로 평가한다. 중요 오류 사례는 평균 점수와 별도로 공개하고, 결과가 나쁠 경우 원인과 수정 범위를 함께 보고한다. 이는 예정된 평가이며 측정 완료 수치를 제시하지 않는다.

## 6. 기대효과

### 기획 검토 시간을 어디에 쓰는지 바꾼다
원문과 제품 기능을 오가며 대조하는 작업을 정리해, 기획자가 잔여 불편의 타당성과 콘셉트 선택에 집중하도록 돕는다. 모든 주요 판단에 원문·모델·불확실성을 연결해 팀원이 결과를 확인하고 수정하기 쉽게 한다. 시간 절감률이나 정확도 향상률은 구현·평가 후 확인할 지표로 남긴다.

### 재사용 가능한 상품기획 절차
냉장고 시연 이후 다른 키친 제품군의 리뷰와 명세를 넣어 같은 입력 계약·조회·대조·검토 절차를 재사용한다. 제품군마다 새로운 기능 용어와 제약을 추가 검증해야 하며, 한 사례의 성공을 모든 가전으로 일반화하지 않는다. 반복 실행 가능한 Agent/Skill, 데이터 사전, 평가 사례, 실행 기록, 근거 기반 콘셉트 제안서를 결과물로 남긴다.

### 성공 판단과 적용 한계
첫 목표는 ‘불편 입력 → 제품 기능 대조 → 후보 생성 → 변경 조건 반영 → 근거와 함께 수정’ 흐름이 다른 입력에서도 작동하는 것이다. 합성 데이터 실험은 논리와 오류 처리 검증에 사용하고, 시장 수요·물리 성능·제조 가능성은 실자료 조사와 분야 전문가 검토 과제로 구분한다. 검토가 필요한 항목을 숨기지 않는 상품기획 보조 도구를 목표로 한다.
