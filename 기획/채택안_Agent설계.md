# 채택안 Agent 설계

2026-09-27. 구현 전 설계이며 모델 성능·시연 완료 기록이 아니다.

## 확정 범위

사용자가 “그걸로 채택했다. 제출 준비하자 서류”라고 직접 채택했다. 후보 `RESET_A_EVIDENCE`, Theme A 고객 불편·기존 제품 대조 기반 키친 상품기획 Agent를 출품 방향으로 확정한다. 기존 Codex의 위임 선정 기록은 역사로 남긴다. 직접 채택이 온라인 접수 완료를 뜻하지 않는다.

직접 사용자는 키친 상품기획자다. 기획 요청과 리뷰·제품 문서가 바뀌어도 니즈 구조화→동일 모델 기능 대조→잔여 불편 확인→콘셉트 작성→검토·수정을 반복한다. 냉장고 수납·정리·청소는 첫 합성 시연 사례이며 주제를 영구 제한하지 않는다.

## 입출력 계약

| 대상 | 주요 필드 | 검사 |
|---|---|---|
| Brief | category, target_user, situation, constraints, exclusions | 빠진 필수 조건 질문, 수치 단위 확인 |
| Review | review_id, product_id, text, date, source, synthetic | 중복 ID 금지, 모델 연결 가능 여부 |
| ProductDocument | document_id, model_id, version, market, text, source, synthetic | 모델·버전 불명확 시 일반화 금지 |
| Evidence | source_id, location, quote, model_id | 원문 존재·구절 일치·모델 일치 |
| Need | situation, pain, desired_outcome, evidence_ids, counter_evidence | 원문과 해석 구분, 빈도를 시장 비율로 쓰지 않음 |
| Comparison | need_id, feature_id, status, rationale, uncertainties | 기존 대응/잔여 불편 가설/근거 부족, 기능 존재≠해결 |
| Concept | need_ids, difference, requirements, constraints, questions | 기존 기능 중복, 근거 없는 효과·제조 가능성 단정 검사 |
| Run | run_id, dataset_version, plan, tool_events, revisions, result, usage | 입력·출력·오류·지연·비용 기록 |

## 최소 실행 구조

Python 실행기 + LLM 1개 + CSV/문서 저장소 + 웹 UI. 초기에는 정규화한 CSV·텍스트·공개 문서 발췌를 사용하고 PDF/OCR 자동화나 대규모 수집을 선행 의존성으로 두지 않는다. 모델 API 연결은 아직 없으며 첫 구현 시 구조화 출력 지원·비용·지연을 확인한다.

| Skill | 입력 → 출력 | 모델/코드 역할 |
|---|---|---|
| evidence_lookup | 검색 조건 → 원문 ID·본문·위치 | 코드는 ID/키워드·모델 필터 조회, 모델이 조회 조건 결정 |
| need_extract | 리뷰 묶음 → 상황·불편·희망 결과 | 모델 의미 분석, 코드는 참조 ID 검증 |
| product_compare | Need + 해당 모델 근거 → Comparison | 모델 조건·차이 해석, 코드는 모델·인용 연결 검사 |
| concept_draft | 잔여 불편 + 제약 → 콘셉트 2~3개/보류 | 모델 기획, 코드는 필수 항목·중복 후보 확인 |
| review_revision | 결과 + 위반/명세 변경 → 수정본·미해결 사항 | 코드의 확정 오류와 모델의 의미 판단을 분리해 기록 |

루프: 요청 검토 → 계획 → 필요한 도구 조회 → 불편/기능 대조 → 콘셉트 작성 → 검사 → 관련 단계 재조회·수정(최대 2회) → 결과 또는 보류. ‘새로운 기능이 반드시 있어야 한다’는 강제 조건은 두지 않는다. 실행기는 스키마/참조 무결성을 보장하고 의미적 정확성은 평가 대상으로 남긴다.

## 실패 처리

- 리뷰가 다른 모델을 가리키면 분리하고 연결을 요구한다. 원문 부족은 해당 기능 미지원으로 바꾸지 않는다.
- 상충 리뷰는 다수결로 지우지 않고 사용 조건과 함께 병기한다.
- 문서 내 지시문은 데이터로만 취급하며 도구 호출 지시로 승격하지 않는다.
- API 실패/한도 도달은 오류와 부분 결과를 반환한다. 모의 응답으로 실제 호출 성공을 위장하지 않는다.
- 수정 2회 후에도 인용 오류가 남으면 해당 결론을 보류한다. 수정 내역과 이유를 보존한다.
- 합성 원천의 표시는 전 단계에 전파한다. 식품 접촉 소재·물리 성능·시장 수요 판단은 전문가 검토 사항으로 남긴다.

## 평가 계획

개발용 예시와 분리한 12개 사례를 만든다: 정상 2, 기존 기능 중복 2, 모델/버전 혼동 2, 상충 의견 1, 근거 누락 2, 명세 변경 2, 문서 내 지시문 1. 별도의 예상 판단·원문 참조를 먼저 작성한다. 동일 모델·자료·출력 계약을 준 강한 단일 프롬프트와 Agent를 각 사례에서 3회 실행한다. 기준선은 별도 도구 반복 없이 완결된 자료와 지시를 제공한다. 두 방식의 토큰/지연/비용 차이도 함께 보고한다.

원문 추적 가능 비율 = 유효한 인용이 붙은 근거 필요 판단 / 전체 근거 필요 판단. 모델 연결 오류·근거 없는 단정·기존 기능 재제안은 항목별 횟수와 사례를 공개한다. 별도 정답이 없는 콘셉트는 실용성·근거 연결·차이 명료성을 사람 평가표로 확인한다. 방식 이름을 가리고 검토 시간을 측정하되 팀 내부 평가의 편향을 명시한다. 실제 기획자 인터뷰는 후속 검증이며 확보했다고 쓰지 않는다.

## 구현 백로그

1. 정규화 입력·샘플 30~50리뷰/3~5가상 모델·자료집 버전과 원천 표기.
2. 조회→대조→콘셉트까지 하나의 실제 모델 호출 흐름, 로그·비용 기록.
3. 스키마/인용/모델 검사, 보류, 수정 상한, 변경 입력 재실행.
4. 요청·근거·대조표·콘셉트·이력 웹 화면과 내보내기.
5. 독립 평가·기준선 비교·핵심 오류 회귀검사.
6. 실행 안내·Agent/Skill 정의서·5분 시연·최종 발표자료.

## 접수용 문서와의 관계

`기획/제출제안서_원고.md`가 공식 6항목 원고다. 개인 연락처·작성된 서명·HWP/PDF는 `private/`에만 저장한다. 양식 작성·파일 열림·페이지 검수와 팀 정보 완비·동의 확인·실제 접수는 각각 별개 상태로 관리한다.
