# Theme A/B와 아이디어 비교

2026-09-27 **1차 비교 기록**. 당시 B1 Kitchen Rehearsal을 추천했으나 사용자는 추가 아이디어 검토를 요청했다. 현재 최종 선택 전이며 [추가 비교](추가아이디어_비교.md)가 최신이다. 팀 환경은 PC·웹 전용이다.

## 먼저 해야 할 일

핵심 하네스를 만든 뒤 오늘 안에 역할·문제·MVP를 결정하고 제안서를 작성해야 한다. 하네스 확장 자체가 목표가 되면 안 된다. 현재 제안서 초안과 주제 비교를 같은 흐름에 연결했다. 동시에 팀명·팀장·서류 정보·서명을 모아야 한다.

## 공식 자료에서 확인한 경계

- 대회 주제 자료 19~20쪽은 A를 상품기획 Agent, B를 UX/UI 시나리오 설계 Agent로 설명한다. 결과물에는 반복 실행 가능한 구현과 시연이 필요하다.
- [LG의 IFA 2026 발표](https://www.lg.com/global/newsroom/news/home-appliance-solution/lg-electronics-unveils-the-next-evolution-of-ai-home-at-ifa-2026/)에는 ThinQ Claw의 상황 이해와 기기·서비스 연계가 소개되어 있다. 범용 가전 비서나 손님맞이 레시피 추천만으로 새로움을 주장하기 어렵다는 판단의 근거다. 출시 지역·모델별 제공 여부를 모두 검증한 것은 아니다.
- [공식 ThinQ MCP](https://github.com/thinq-connect/thinqconnect-mcp)는 계정 토큰·국가 코드와 장치 프로필 기반 제어를 전제로 한다. API가 존재해도 우리 팀이 특정 장치를 실제 제어할 수 있다는 뜻은 아니다.
- 고객·기획자의 불편 크기나 지불 의향은 아직 실증하지 않았다. 아래 문제는 검증할 가설이다. LG 내부에 유사 도구가 없다고 주장하지 않는다.

## 테마 비교

| 기준 | Theme A: 상품기획 Agent | Theme B: UX/UI 설계 Agent |
|---|---|---|
| 목표 | 고객 신호·기술 근거로 새 제품 기회를 제안 | 상황·가전 제약으로 연결 경험을 설계·점검 |
| PC 구현 | 가능 | 가능 |
| 주요 데이터 | 리뷰·VOC·시장·논문·특허 | 기기 기능 명세·설계자 입력·시나리오 |
| 내일까지의 약점 | 유의미한 고객 신호 확보와 차별화 근거에 시간 필요 | 시나리오 도구의 효용을 설득하고 실체 있는 검증을 보여야 함 |
| 평가 가능성 | 근거 추적·중복·기획 품질; 전문가 판단 의존 큼 | 기능 제약·시간 충돌 등 정량 검사 + 설계자 사용성 검증 |
| 위험 | 스크래핑·빈약한 표본·특허 신규성 과장 | 합성 시뮬레이션을 실제 고객 검증으로 오해할 위험 |
| 현재 판단 | 유력 대안 | **조건에 더 잘 맞는 추천** |

B가 본질적으로 더 높은 점수를 받는다는 뜻은 아니다. PC 전용·내일 접수·팀 3명이라는 현재 제약에서 구현 경로와 검증 방법이 더 선명하다는 판단이다.

## 추천안의 한 문장

**주방 UX 기획자가 고객 상황과 가전 기능을 입력하면, AI가 연결 시나리오를 설계하고 충돌·미지원 동작·실패 경로를 검사·수정하여 화면 흐름과 검증 기록까지 만드는 Agent.**

핵심 사용자는 주방을 쓰는 소비자에 앞서 그 경험을 설계하는 기획자다. 결과물에는 소비자가 경험할 미래 키친 시나리오도 포함한다. '오븐을 제어하는 챗봇'과 달리, 시나리오 설계 업무의 반복 작업을 수행하도록 범위를 잡는다.

## 추천의 전제와 바뀔 조건

- 실기기·기업 내부 데이터·대규모 수집 없이 최소 검증을 시연할 수 있어야 한다.
- 입력에 따라 계획하고 검사 결과로 수정하는 LLM 루프를 구현해야 한다. 현재의 규칙 검사 예제만으로 참가작이 완성되는 것은 아니다.
- 실제 기획자 요구 확인이 부족하다. 9/27에는 가능한 지인·학생 설계 과제 사용성 검토를 하고, 선발 후 LG 컨설팅에서 현업 문제를 확인한다. 실제 참여자가 없으면 수행했다고 쓰지 않는다.
- 모델 API의 사용 가능성과 비용 한도는 아직 확인 전이다. 공식 API 또는 팀 PC에서 작동하는 모델 중 하나의 실제 호출을 개발 초기에 검증한다. Codex 구독을 앱 API 사용권으로 가정하지 않는다.
- 사용자가 A를 더 선호하면 A1으로 바꿀 수 있다. 데이터 확보가 먼저이며 하네스는 그대로 사용한다.
