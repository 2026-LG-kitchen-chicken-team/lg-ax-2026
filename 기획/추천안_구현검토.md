# Kitchen Rehearsal 구현 검토

> 미선정 후보의 보관 기록이다. 현재 선정안은 Theme B Kitchen Recovery이며 `AtoZ_재선정과_Agent설계.md`를 따른다. 아래 범위·상태는 당시 검토 기록이다.

상태: Theme B 추천안, 최종 선택 전. PC·웹 전용. 실제 구현 위험을 없다고 보장할 수는 없으므로 핵심 의존성과 축소 경로를 먼저 정리한다.

## 문제와 고객 가치

가설: UX 기획자가 주방 경험을 설계할 때, 가족 상황·기기 기능·순서가 바뀔 때마다 정상 흐름과 실패 흐름을 다시 만드는 수고가 있다. 이를 줄이는 설계 Agent를 만든다. 실제 현업 소요시간·불편 빈도는 아직 측정하지 않았다.

최종 사용 경험 예시: 손님 방문 시간이 바뀌고 오븐 한 대를 두 요리에 써야 하는 상황에서, 기획자가 소비자 안내·대기·재확인 흐름을 함께 설계한다. 실제 조리시간이나 식품 안전을 검증하는 제품은 아니다. 사용자가 제공하는 시간은 설계 가정으로 표시한다.

## 입력과 출력

입력: 사용자 상황, 목표, 시간·우선순위, 사용 가능한 장치와 지원 기능, 사람이 해야 하는 작업, 실패 이벤트. 기기 명세는 모델명·지역·근거 URL·확인일·모의 여부를 가진다. 공개 SDK의 일반 기능 목록을 모든 실기기의 지원 기능으로 간주하지 않는다.

출력: 서비스 시나리오, 행동 순서와 사람 확인 지점, UX 화면별 안내 문구, 발견된 충돌과 수정 이유, 근거 연결, 재실행용 JSON, 테스트 케이스. 추천 메뉴 자체가 핵심 산출물은 아니다.

## 최소 Agent 흐름

1. **조건 정리 Skill**: 자연어를 구조화. 누락된 필수 조건은 질문하거나 명시적인 가정으로 보류.
2. **기능 확인 Skill**: 출처가 있는 기능 목록에서 허용 동작 조회. 알 수 없는 동작은 미지원/확인 필요로 반환.
3. **시나리오 설계 Skill**: 목적과 조건에 맞는 단계·분기·화면 흐름 작성.
4. **제약 검사 Skill**: 선후 관계·자원 충돌·미지원 동작·실패 분기 누락 등 검사. 판단 가능한 규칙은 코드로 처리.
5. **수정·출력 Skill**: 모델이 검사 결과를 반영해 수정. 최대 2회 후에도 해결 안 되면 미해결 보고와 설계자 확인으로 종료.

Agent가 어떤 도구를 왜 호출했는지 구조화 로그로 남긴다. 모델 내부 사고 과정을 수집하거나 공개하는 기능은 필요 없다.

## 지금 확인할 수 있는 기술적 부분

`scripts/scenario_spike.py`는 합성 기능 목록과 가정한 시간을 사용해 동작 지원 여부·순서·동시 자원 사용을 검사한다. 정상/충돌/미지원 입력을 바꿔 반복 실행할 수 있다. 순환 의존성도 검사한다.

이 예제는 **제약 검사부의 실현성 확인**이다. LLM 호출, 자동 시나리오 생성·수정, 실제 기기 연동, 실제 사용자 효용은 검증하지 않았다. 자세한 실행 결과는 `docs/하네스_검증기록.md`에 기록한다.

## 구현 범위와 축소 순서

| 구분 | 내용 |
|---|---|
| 필수 MVP | 웹 입력 폼, LLM 1개 연결, 구조화 시나리오, 기능 명세 3종, 규칙 검사, 2회 이내 수정, 결과·로그 출력 |
| 초기 시나리오 | 식사 준비 1개 여정, 시간 변경/장치 미지원/사용자 응답 없음 등 3종 변형 |
| 데이터 시작점 | 공개 자료에서 사람이 검토한 기능 명세 + 명확히 표시된 합성 프로필. 고객 데이터로 위장하지 않음 |
| 후순위 | Figma 자동 출력, 실시간 크롤링, 대규모 RAG, 계정·조직관리, 실기기 제어, 사용자 행동 예측 |
| 시간 부족 시 | 도식 자동 배치를 표 형태로, PDF 내보내기를 Markdown/JSON으로, 가전 종류를 2종으로 축소 |

구현 기술 제안: Python 기반 Agent/검사 로직 + 간단한 웹 UI. 웹 프레임워크는 선정 뒤 팀 경험과 모델 연결을 보고 정한다. 지금 Next.js나 복잡한 서비스 분할을 선결정하지 않는다.

## 평가 계획

- 개발용 12개와 별도 평가용 12개의 합성 케이스를 준비하는 것을 목표로 한다. 현재 확보한 케이스 수가 아니다.
- 정상/자원 충돌/시간 변경/미지원 기능/누락 조건/오프라인 이벤트를 포함한다.
- 검사 정확도는 팀이 검토한 정답과 비교한다. 규칙 검사 성공을 사용자 만족도 성공으로 바꾸어 쓰지 않는다.
- 같은 모델·같은 입력으로 단순 1회 생성과 검사-수정 Agent를 비교: 제약 위반 수, 누락 조건 처리, 실행 성공률, 지연, 비용.
- 시나리오의 유용성은 사람이 별도 평가한다. 가능하면 3~5명 설계 과제에서 시간·수정 횟수·이해도를 관찰하되 표본 한계를 명시한다.
- 프롬프트로 검토 정답을 주입한 케이스와 독립 평가를 구분한다.

## 위험과 대응

| 위험 | 상태 | 대응 / 확인 시점 |
|---|---|---|
| 사용할 모델·API 키·비용 한도 | 미확인 | 구현 첫날 실제 한 번 호출하고 비용·구조화 출력 확인. 실패하면 사용 가능한 공급자/로컬 모델로 변경 후 같은 평가 |
| LG 실기기/API | 사용할 수 없음(PC 전용) | 핵심 구조가 의존하지 않도록 설계. 모의 기능을 실제 제어로 표시하지 않음 |
| 모델별 기능 데이터 | 아직 미정 | 2~3개 프로필부터 출처 대조. 불명확한 기능을 자동 허용하지 않음 |
| 실제 기획자의 수요 | 가설 | 제안서에서 가설로 표기, 컨설팅에서 검증 |
| 기존 도구와의 차별성 | 제한적 공개 조사 | 근거 연결·기능 제약·반복 검사·재사용 출력에 초점. 세계 최초/사내 미보유 주장 금지 |
| 모델이 없는 기능 생성 | 예상 위험 | 허용 목록 검사와 최대 재시도, 미해결 상태 공개 |
| 물리 조리 정확도 | 범위 밖 | 작업 시간은 가정, 고객 안전·식품 상태 판정에 사용하지 않음 |
| 화면·생성 범위 확대 | 일정 위험 | 한 여정·세 변형·핵심 화면만 MVP |
