# 사용자 목표에 따른 재선정과 Agent 설계

2026-09-27. 사용자 정정: **쉽게 설계·완주하면서 심사 경쟁력이 높은 아이디어**, 그리고 탐색부터 설계·구현·평가·제출까지 연결되는 하네스를 원한다. 기존 Kitchen Gap은 자료 확보 편의와 규칙 검사에 비해 개방형 상품기획의 평가 부담을 충분히 반영하지 못했다. 기존 선정은 역사 기록으로 보존하고 최신 목표로 재검토했다.

## 현재 선택: Theme B · Kitchen Recovery

**사용 상황과 가전 기능을 입력하면, 정상 흐름뿐 아니라 통신 실패·미확인·사용자 미응답 상황의 UX를 설계하고, 누락된 분기를 검사·수정해 흐름과 화면 명세를 내놓는 Agent.**

사용자는 주방 서비스 UX 설계자다. 예를 들어 '귀가 전에 주방 준비 상태를 확인하는 경험'을 요청하면 Agent가 필요한 상태·확인·실패 안내를 설계한다. 완성될 참가작은 가전 제어 앱보다 UX 설계 산출물을 만드는 업무 도구에 해당한다. 기기 제어·실제 조리 안전 판단은 초기 구현 범위에 포함하지 않는다.

식기세척기로 한정하지 않는다. 조리 기기와 보관 기기의 연결/확인 상황을 개발용 사례로 사용한다. 예시 오븐 모델의 조건은 해당 모델에만 적용하며, 냉장고 상태 사건은 합성 입력으로 표시한다.

## 같은 기준으로 다시 본 7개 후보

| 후보 | 설계·평가 부담 | 경쟁력을 보여줄 지점 | 판단 |
|---|---|---|---|
| A4 Kitchen Gap | 원문 의미 대응, 기회 가치·신규성 평가가 개방적 | 반대 근거와 기획 카드 | 대안 보관 |
| A6 Kitchen Fit | 정확한 공간·설치 명세 필요 | 생활 조건별 제품 공백 | 보류 |
| A2 Cross-Tech Scout | 기술 전이 실현성 검증이 어려움 | 논문/기술 기반 기획 | 보류 |
| **B7 Kitchen Recovery** | 출력이 상태·분기 구조로 제한됨. 모델 생성은 여전히 검증 필요 | 실패 주입→누락 발견→수정 전후→다른 상황 재실행 | **선정** |
| B6 First Kitchen | 생성은 쉬움, 이해도 효과 측정 필요 | 상황별 안내·학습 | 기존 안내와 차별성 약함 |
| B4 Kitchen Relay | 상태 처리는 가능, 다인 사용자 수요 확인 필요 | 미응답·중복 담당 복구 | 근거 보강 필요 |
| B1 Kitchen Rehearsal | 범용 일정·물리 가정·화면 생성으로 범위가 넓음 | 자원 충돌 검사 | B7로 범위를 구체화 |

새 이름만 늘린 탐색은 피했다. 6개는 기존 후보의 재평가이고 B7은 B1에서 시간 계획·자원 최적화 범위를 줄여 실패 UX 설계에 집중한 후보다. 공식 배점·경쟁팀·심사위원의 선호를 모르므로 **수상 확률 1위가 입증됐다는 뜻은 아니다**. 현재 근거에서 설계 부담과 과제 적합성·시연 전달력을 함께 고려한 최선의 작업 선택이다.

## 근거와 실행 결과

- LG의 특정 오븐 설명서에는 원격 시작 전제와 통신 지연 조건이 있다. 이는 실패 분기 설계에 사용할 실제 조건의 사례다. [MFL71927512, 22~23쪽](https://gscs-b2c.lge.com/open/downloadFile?fileId=tYJHqI7Nk3lkQwrvv6IRQ)
- Figma Make가 일반 흐름 생성을 제공하므로 **화면 생성 자체는 차별점에서 제외**한다. 적용 범위가 표시된 가전 조건, 실패 사건, 반례와 수정 이력을 결과에 포함하는 데 집중한다. 이 조합의 세계 최초나 경쟁 도구의 미지원은 주장하지 않는다. [Figma 공식 설명](https://www.figma.com/solutions/ux-flow-generator/)
- `research/atoz/flow_trials.json`의 결함을 주입한 2개 개발용 그래프에서 검사기가 각각 4개·3개 문제를 반환했다. 수정본에서는 해당 검사 위반이 0개였고 7개 이벤트 경로가 기대 상태에 도달했다.
- 그 결과는 `scripts/flow_audit.py`로 재현된다. Codex가 그래프와 요구 조건·수정본을 작성했다. 별도 LLM API의 생성 정확도나 실제 기기 실패 복구 성능을 측정한 실험은 아니다.
- A4/B1의 이전 규칙 검증도 비교에 재사용했다. 테스트 개수만으로 후보 우열을 결정하지 않았다.

현업에서 이 오류가 얼마나 자주 발생하고 시간을 얼마나 절감할 수 있는지는 아직 가설이다. LG 컨설팅과 설계 과제로 보완한다.

## 최소 Agent 구조

모델은 하나로 시작한다. 다음 흐름을 하나의 실행기로 연결하며 다중 Agent·벡터 DB·실기기 계정은 필수로 넣지 않는다.

`사용 목표 + 검토된 기능/조건 → 구조화 → UX 그래프 초안 → 코드 검사·이벤트 실행 → 모델 수정(최대 2회) → 결과 또는 미해결 보고`

| 구성 | 입력 | 출력/책임 |
|---|---|---|
| 입력 정리 | 자연어 상황·대상 모델·기능 계약 | 목표, 확인된 상태, 모르는 정보. 추정값 표시 |
| 조건 조회 Skill | 기기/모델·동작 | 해당 범위의 출처·지원·전제. 미확인 반환 가능 |
| 설계 모델 | 목표·조건·필수 실패 사건 | JSON 상태/전이/화면 문구/출처 |
| 구조 검사 Skill | 그래프 JSON | 깨진 연결, 도달 불가, 실패 분기 누락, 무근거 명령 계약 |
| 이벤트 실행 Skill | 그래프·개발/평가 사건 | 상태 경로·기대 결과와 차이 |
| 수정 모델 | 초안·검사 오류·원래 목표 | 수정된 그래프 또는 해결 불가 사유 |
| 출력 | 마지막 그래프·기록 | 화면 흐름, 오류 전후, 출처·가정·미해결 목록 |

현재 `flow_audit.py`는 구조와 명시적으로 주어진 계약의 일부만 검사한다. `requires` 목록이 존재하는지 확인하지만 그 조건의 물리적 충족까지 증명하지는 않는다. 실제 참가작에서는 조건 값/unknown과 명령 경로의 전제 충족을 추가 검사해야 한다.

## 데이터 계약

입력: `goal`, `context`, `capabilities[{model, region, action, preconditions, source_id}]`, `known_state`, `failure_events`.

출력: `nodes[{id, kind, text, source_ids}]`, `transitions[{from,event,guard,to}]`, `assumptions`, `unresolved`, `screen_specs`, `execution_log`.

임의 코드를 모델이 생성해 실행하는 구조는 사용하지 않는다. 서버는 정해진 JSON 상태·이벤트만 해석한다. 그래프 크기와 실행 단계 수를 제한한다. 실험 출력의 `done`은 해당 UX 확인 단계의 완료이며 식품 조리 완료나 안전을 뜻하지 않는다.

## 실패 처리

- 모델/기능 미확인 → 필요한 정보를 질문하거나 해당 동작을 제외한 설계 초안.
- API 오류·시간 초과 → 원문 입력과 마지막 결과 보관, 재시도 한도 후 실패 보고.
- 구조화 출력 오류 → 스키마 오류를 전달해 수정, 최대 2회 후 미해결.
- 검사 미통과 → 통과한 것처럼 숨기지 않고 문제 노드 표시.
- 사용자 미응답·기기 확인 없음 → 완료로 처리하지 않는 UX 분기.
- 특정 모델 조건을 다른 모델에 전용 → 보류/범위 오류.

## 구현과 검증 순서

1. **세로 기능**: 한 입력→실제 모델 JSON→코드 검사→한 번 수정→결과. 첫 단계에서 API 설정과 비용 확인.
2. **단일 화면**: 왼쪽 입력, 가운데 흐름/문구, 오른쪽 오류·근거·수정 이력. 처음에는 카드와 표로 구현 가능.
3. **재사용**: 조리/보관 두 상황과 조건 변경, 출처가 없는 동작 처리.
4. **평가**: 개발용과 분리된 정상·offline·unknown·timeout·모델 불일치·추가 사건 케이스. 단순 1회 생성과 같은 모델/입력으로 비교.
5. **측정**: 구조 위반 수, 사건 경로 처리율, 수정 성공/실패, 실제 호출 비용·지연. 기획자의 유용성 평가는 별도.
6. **발표**: 정상 흐름→실패 사건→누락 발견→수정→다른 상황 재실행을 보여준다.

역할 배분은 팀원의 경험과 시간 확인 후 정한다. 프로토타입 목표는 수일 단위의 작은 흐름이지만 전체 작업시간을 확정하지 않는다. API 연결·LLM 출력 안정성·사용자 효용은 남은 위험이다.

## 현재 상태

AtoZ 하네스의 12단계 실행 계약과 재개 도구를 구축했다. 이 대화에서 목표 정렬·조사·발산·비교·규칙 실행·재선정·Agent 설계까지 수행했다. 신청서·실제 모델 연동·사용자 평가·발표·제출은 완료하지 않았다. 다음 접수 작업은 이 선정안의 공식 6항목 제안서다.
