# Theme A·B 각각의 최종 후보 선정

2026-09-27 · 선정자 Codex · 사용자 요청: 기존 12개를 1차 서류 경쟁력, 구현 난도, 실제 사용 가치 등으로 평가하고 테마별 하나를 선별.

**Theme A는 공식 두 번째 과제의 A②, Theme B는 공식 네 번째 과제의 B④를 선정한다.** 이 문서의 번호는 공식 표의 행 번호다. 내부 ID는 ROW_A2/ROW_B4이며 과거 A8/B8과 이어진다. 두 후보를 뽑으라는 위임에 따른 판단이며 사용자가 이 아이디어를 직접 승인한 기록은 아니다. 최종 출품 테마 하나의 결정·신청 완료와도 구분한다.

## 평가 방법과 증거 수준

공식 신청서는 개요, 배경, 활용 정보, 아이디어와 차별성, 구현·사업화 방향, 기대효과를 요구한다. 추가 주제 자료의 전체 평가 관점은 Problem / Insight / Agentic Process / Implementation / Reuse & Value다. **공개된 별도의 1차 배점표나 합격 확률은 없다.** 따라서 아래 ‘서류 설득력’은 지금 확보한 근거로 이 항목들을 연결해 설명하기 얼마나 좋은지에 대한 상대 판단이다. 완성 Agent가 접수 시 필수라는 뜻은 아니다.

평가 기준은 ① 공식 과제와 Agent 직무 적합성 ② 문제·근거·차별성의 서류 설득력 ③ 모델·코드·화면 구현 부담 ④ 데이터 확보 및 외부 의존성 ⑤ 직접 사용자에게 반복되는 업무인지 ⑥ 강한 LLM·기존 서비스 대비 추가 가치 ⑦ 오류를 검사하고 시연할 수 있는지다. 임의 배점의 합계를 합격 확률처럼 제시하지 않는다.

- **직접 사용자:** A는 가전 상품기획자, B는 키친 서비스·UX 기획자/디자이너. 가정의 소비자는 기획 결과의 최종 수혜자다. 소비자가 서비스를 좋아할 것 같다는 판단과 기획자가 Agent를 실제 쓰겠다는 판단을 나눴다.
- **구현 범위:** 반복 실행되는 기획·설계 Agent와 산출물의 작은 시뮬레이션. 물리 가전 제조, 실제 조리 자동화, 실기기 제어를 모두 구현하는 범위가 아니다.
- **공통 전제:** PC에서 모델·도구·웹 화면을 연결하고 팀이 기본 웹/Python 구현을 할 수 있다는 계획 가정. 실제 개발 숙련도·모델 API 환경은 미확인이다.
- **조사:** 12개에 대한 기존 공식/경쟁 자료 비교를 재사용하고 상위 두 후보의 실제 제품 명세 접근과 계산 기능을 추가 확인했다. 12개 모두를 실제 구현해 성능 비교한 것은 아니다.
- **미확인:** 12개 모두 현업 사용자 인터뷰·독립 평가자 검토·강한 LLM과의 통제 비교가 없다. 실사용 평가는 가설이다.

## A 선정: 작은 주방의 제약을 제품 기획으로 바꾸는 Agent

**주제명: 1~2인 가구의 주방 공간·생활 조건에 맞춘 가전 폼팩터 기획 Agent.**

공식 대응: ‘미래 라이프스타일과 가구 형태 변화에 따른 가전 및 폼팩터 제안’.

상품기획자가 고객군의 주방 공간·필요 용량·사용 상황과 제품 명세를 넣으면, Agent가 기존 제품이 요구를 충족하는지 대조하고 반복되는 미충족 조건을 찾는다. 그 결과를 근거로 폭·깊이·문 개폐 방식·수납 접근 등 **검토할 제품 형태와 서비스 콘셉트**를 제안하고, 어떤 자료에서 나왔는지와 추가 검증 항목을 붙인다. 기존 제품이 이미 해결하면 새 제품이 필요한 것처럼 만들지 않는다.

예시: ‘작은 주방인데 저장 용량은 필요하고, 제품은 들어가도 문 앞 동선이 좁다’는 조사 사례가 있을 때, 제품 본체 치수와 문 열림 조건을 분리해 검사한다. 고객 조사에서 이 문제가 반복되는지 확인한 뒤 대체 개폐 구조나 공간별 구성안을 기획 과제로 제시한다. **이 상황의 빈도·시장 규모는 아직 조사하지 않았다.**

선정 이유:

1. 고객 상황→기존 제품 한계→새 제품 방향→Agent의 검증 역할이 공식 A 과제와 직접 연결된다.
2. 숫자와 출처가 맞는지 코드로 확인할 수 있어 문장 생성만으로 끝날 위험을 줄인다.
3. 고객군·공간·제품군이 바뀔 때 비교표와 콘셉트를 다시 작성하는 상품기획 업무를 대상으로 한다. 다만 현업에서 충분히 자주 하는지는 확인이 필요하다.
4. 기존 작은 주방/Zero Clearance 제품을 비교군으로 넣어 ‘이미 있는 기능의 재제안’을 걸러낼 수 있다. 이것이 차별성을 입증한 것은 아니다.

**최소 구현:** 검토된 한 제품군 5개 내외 명세와 공간 사례 3개를 시작 데이터로 사용한다. 자연어 조건 정리→출처가 연결된 데이터 조회→치수/누락 검사→미충족 요구와 기존 대안 비교→콘셉트 카드 생성→제약 위반 검사·수정→입력 변경 재실행. CAD·사진 자동 실측·제조 가능성 보증은 초기 구현에 포함하지 않는다. Agent 산출물은 설치 승인서가 아니다.

**핵심 어려움:** 제품별 문 열림 조건과 치수 표기 차이, 자료 추출 정확도, 고객 수요 자료, ‘제품 추천표’에서 ‘신제품 콘셉트 기획’으로 넘어가는 근거다. 앞의 두 개는 데이터 범위를 줄여 다룰 수 있으나 수요를 합성 사례로 대체해서는 안 된다.

**이번 확인:** LG 공식 미국 제품 명세 PDF 2종에서 수치를 수동 구조화했다. 가상 공간 4개×2모델의 8개 조합에서 폭·높이·문 열림 폭 검사, 정보 누락 보류, 시장 불일치 보류가 실행됐다. 웹 제품 페이지의 표 추출은 불안정했으므로 자동 크롤링 성공을 전제하지 않고 검토된 PDF/구조화 데이터부터 시작한다.

두 명세는 2021/2022년 개정 미국 대형 냉장고 자료다. **이 실험은 공개 치수로 계산하는 경로를 확인했을 뿐, 현재 국내 1~2인 가구 제품군·미충족 시장을 검증하지 않았다.** 깊이·반입 경로·배관·옆 벽 간섭·서랍 꺼냄 등은 아직 계산하지 않는다. 다음에는 국내 대상 제품의 정확한 모델/개정 문서와 실제 조사 사례를 확보해야 한다.

## B 선정: 가전 연계 식사 준비의 충돌·지연을 재설계하는 Agent

**주제명: 가전 자원과 조리 지연을 반영하는 식사 준비 UX 시나리오 설계 Agent.**

공식 대응: ‘가전 간 연계를 통한 AI 기반 키친 서비스’.

UX 기획자가 사용할 가전·사람 수·요리의 작업 순서·목표 식사 시각을 입력하면, Agent가 작업과 자원 사용을 구조화하고 충돌을 검사한다. 조건 변경 시 가능한 순서를 다시 계산하고 **사용자에게 보여줄 일정·알림·확인/선택 화면과 예외 흐름**을 다시 설계한다. 제안하는 소비자 경험은 서로 다른 조리 가전과 사람의 일을 연결해, 바뀐 식사 준비 계획을 이해하고 선택하게 하는 서비스다.

예시: ‘오븐과 인덕션으로 두 메뉴를 준비하는데 오븐 작업이 늦어졌다.’ Agent는 다른 작업까지 단순히 같은 시간만큼 미루지 않고 선행 관계·작업자·가전 점유를 확인한다. 목표 시각을 못 맞추면 불가능 이유를 표시하고, 이미 검토된 대안의 선택 화면을 설계한다. 시작하거나 끝난 작업을 다시 수행시키지 않는 상태 처리도 필요하다. 현재 계산 실험은 이 전체 경험을 구현하지 않았다.

선정 이유:

1. 가전 간 연계가 왜 필요한지 작업 충돌과 상황 변경으로 설명하기 쉽다. ‘기기를 연결한다’는 추상적 제안보다 심사에서 보여줄 전후 상황이 명확하다.
2. UX 설계 Agent가 한 번의 이야기를 쓰는 대신 여러 입력에서 생성→검사→수정→화면/평가 사례 산출을 반복하도록 만들 수 있다.
3. 실기기 없이도 이 **설계 업무 자체**는 PC에서 구현·검증할 수 있다. 소비자용 가전 제어가 실제로 연결되었다고 주장하지 않는다.
4. 상태·자원 충돌·불가능 조건은 정답 기준을 정의하기 쉽고 발표에서 실패 후 수정까지 보여주기 좋다.

**최소 구현:** 검토된 요리 2~3개, 가전 2종, 작업자 1명, 한 시연의 작업 6~8개로 제한한다. 요구사항 해석→작업 그래프 생성→자원/선행 관계 검사→계산→충돌·미확인 정보의 추가 질문→타임라인·UX 화면·테스트 사례 생성→변경 조건으로 재검사. 현재 8개 이하 탐색 코드는 작은 검증용이다. 규모를 늘릴 때는 OR-Tools 등으로 바꾸고 별도로 성능 검증한다.

**핵심 어려움:** 실제 요리를 능동 작업/자동 조리로 나누는 메타데이터, 작업 시간 근거, 수행 중인 작업 상태 보존, LLM 출력과 계산 결과·화면의 일관성이다. 제약 계산기의 기여와 Agent의 기여를 구분해야 한다. 계산 결과를 읽어주는 챗봇만 만들면 약하다.

**이번 확인:** 작업자 1명·오븐 1대·가상 작업 6개로 정상/시간 증가/가전 사용 불가/시간 누락/불가능 마감/순환 의존의 6개 사례를 실행했다. 산출 일정에서 자원 중복·선행 위반이 없는지 별도 검사했다. 정상 총 길이는 25, 시간 증가 후 33이었고 마감 30을 못 맞춘다고 반환했다. **가상 시간 단위이며 실제 조리 시간·절감 효과가 아니다.** 한 가전의 핵심 제약 실험이므로 가전 2종 연계 전체, 실제 상태 수신, 진행 중 작업을 고정한 재계획은 후속 구현이다.

## ‘그냥 LLM 쓰면 되는 것 아닌가’에 대한 선정 조건

두 후보 모두 LLM보다 낫다는 실측은 아직 없다. 모델이 조건을 읽고 초안을 만들고, 코드가 확인 가능한 제약을 검사하고, Agent가 오류를 근거로 수정하여 작업 산출물을 만드는 구성을 택한다. 추가 구성의 비용보다 편익이 커야 채택할 이유가 생긴다.

선발 후 비교할 기준선은 같은 자료·조건을 준 **강한 LLM 단일 프롬프트**, **수동 구조화+계산 도구**, **전체 Agent**다. 모든 방식에 같은 품질 기준과 시간을 적용한다. 쉬운 예제만으로 차이를 부풀리지 않는다.

| 후보 | 측정할 품질 | 측정할 업무 부담 | 선정 재검토 조건 |
|---|---|---|---|
| A② | 인용/단위 오류, 미확인 정보 단정, 이미 있는 기능 중복, 콘셉트와 제약의 모순 | 새 제품·공간 추가부터 검토 가능한 콘셉트까지 총 시간과 수동 수정량 | 대상 시장 명세·고객 사례 확보 실패, 추천표 수준에 머묾, 현업 반복 업무가 아님 |
| B④ | 자원·선행 위반, 불가능 조건 처리, 화면과 일정 불일치, 진행 중 작업 보존 | 조건 변경부터 검토 가능한 UX 산출물까지 총 시간과 수동 수정량 | 조리 작업 데이터가 부실, 기획자가 산출물을 못 씀, 단순 계산기보다 추가 가치가 없음 |

표본 수·성공 기준은 구현 전에 고정하고 현업 검토자를 섭외한다. 확보하지 못하면 ‘팀 내부 탐색 평가’로 제한해 보고한다. 아직 고객 인터뷰나 현업 채택을 검증했다고 적지 않는다.

## 비교 결론과 다음 작업

**A②는 근거를 갖춘 상품기획 산출물을 만들기 좋고, B④는 반복 Agent 과정과 오류 수정을 보여주기 좋다.** 가장 쉬운 후보만 고르면 B⑤ 쪽이지만 기존 기능과 차이를 설득하기 어렵다. 가장 화려한 후보를 고르면 A⑤가 유리할 수 있으나 신뢰성 검증 부담이 크다. 현재 환경·기한에서 서류와 이후 구현의 균형을 우선해 A②/B④를 선택했다.

테마별 선별은 완료했다. 출품은 A/B 중 하나를 택하는 별도 결정이며 신청서·제안서·접수 완료 기록은 변경하지 않는다. 출품안 선정 후 공식 6항목 원고를 작성하고 팀 정보·서명을 취합해 오늘 접수 목표로 이어간다. 두 안을 병렬 구현하거나 새로운 아이디어 탐색을 계속 늘리는 계획은 아니다.
