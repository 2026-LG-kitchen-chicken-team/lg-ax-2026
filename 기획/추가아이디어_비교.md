# 추가 아이디어 비교: 실제 주방의 수고에서 출발

> 보관 기록: 이후 사용자 목표에 따라 재검토하여 Theme B Kitchen Recovery를 선정했다. 현재 기준은 `AtoZ_재선정과_Agent설계.md`다. 아래 미확정·PC 전용 표현은 당시 비교 조건이다.

2026-09-27. 사용자가 Kitchen Rehearsal 확정 대신 추가 후보 검토를 요청했다. **현재 주제는 미확정**이며 기존 B1 원고는 보관용 후보 초안이다. 이번 비교는 PC·웹 전용 조건에 맞춘 신규 후보 5개다.

## 이번 조사에서 새로 확인한 점

1. [LG 적재 안내](https://www.lg.com/us/support/help-library/lg-dishwasher-loading-the-dishwasher--20151129117242)는 그릇 배치와 분사·세제 투입부 방해를 확인하도록 설명한다. 기기를 사용하면서 사람이 판단하고 정리하는 단계가 존재한다는 근거이며, 얼마나 자주 불편한지는 이 문서로 알 수 없다.
2. [건조 후 물 잔류 안내](https://www.lg.com/us/support/help-library/lg-dios-dishwasher-there-is-water-left-on-the-dishes-even-after-dry-has-finished--20154848491113)는 적재·재질·환경 등 조건을 구분한다. 모델 공통 안내를 특정 최신 제품의 성능 결함으로 해석하지 않는다.
3. [2026 신형 식기세척기 발표](https://www.lg.com/global/newsroom/news/home-appliance-solution/lg-electronics-to-showcase-new-dishwasher-lineup-at-eurocucina-2026/)는 세척·건조 개선과 오염도 기반 자동 조절을 소개한다. 따라서 단순히 'AI가 세척 코스를 추천한다'는 아이디어는 기존 기능과 먼저 비교해야 한다.
4. [LG Design for All](https://www.lg.com/global/sustainability/design-for-all/)에는 쉬운 사용 안내와 교육 활동이 소개되어 있다. 쉬운 설명서만 제공하는 서비스 역시 차별성을 추가로 확인해야 한다.

문서의 존재는 문제 가능성과 현재 요구되는 행동을 보여준다. 소비자 전체의 불만 빈도·수요·절감 효과는 아직 미확인이다. 공식 안내 사이에 차이가 있으면 국가·모델·세대·작성 시점부터 확인하며, 바로 모순이나 결함이라고 결론 내리지 않는다.

|---|---|---|---|---|
| A4 | **주방 잔여수고 발굴 Agent** | 새 제품/서비스 기획안 + 출처 + 기존 기능 대비 남은 공백 | 설명서·지원문서에서 사람이 해야 하는 일을 추출하고 여정별 묶음 → 기존 제품 기능으로 이미 해결했는지 반박 → 미해결 가설과 콘셉트 생성 | 검토된 작은 문서 묶음으로 시작 가능. 고객 니즈 검증 없이 인기·수요를 단정하면 안 됨 |
| A5 | **생활조건별 기능 공백 탐색 Agent** | '이런 가구·생활조건에서는 어떤 기능이 부족한가' 비교표와 제품 제안 | 1인 가구·작은 주방·불규칙 식사 등 입력 → 공개 제품 명세와 조건 대응 → 기능 조합 공백 탐색 | 입력 조건과 명세로 구현 가능. 대표성·공간/하드웨어 타당성은 별도 검증 |

| B5 | **Dish-to-Done: 설거지가 끝나는 순간 설계** | '세척 종료' 후 분류·확인·정리까지 이어지는 안내 흐름 | 사용자의 목표와 식기 상태 입력 → 기계 작업/사람 작업 분리 → 미완료·물 잔류·지연 시 대응 UX 작성 → 시뮬레이션 | 식기세척기 한 여정으로 좁아 구현 용이. 사진만으로 재질·세척 가능 여부를 자동 확정하지 않음 |
| B6 | **First Kitchen: 첫 사용 적응 Agent** | 처음 쓰는 가전의 상황별 짧은 안내와 연습 화면 | 설명서·경험 수준·오늘 할 일 입력 → 개인별 사용 시나리오 생성 → 선택 오류에 따라 다음 안내 수정 → 이해도 검증 | 학생 대상 사용성 과제 가능. 기존 쉬운 설명서·지원 챗봇과의 차별성이 관건 |

## A4를 예로 보면

문제 입력: **'식기세척기가 끝나도 사람이 다시 판단하고 처리해야 하는 일이 무엇인가?'**

1. 지원문서 10~20개를 사람이 범위·버전을 확인해 넣는다. 지금 10~20개 전체를 확보한 상태는 아니며, 초기 근거 5개를 `research/problem_signals.json`에 기록했다.
2. Agent가 적재 확인, 물 잔류 확인, 필터 관리 등 인간 작업을 문서 위치와 함께 추출한다.
3. 최신 제품 소개와 대조해 이미 해결한 기능은 제외하거나 조건부로 표시한다.
4. 남은 문제 가설에 대해 제품 기능·부가 서비스 콘셉트와 검증할 질문을 만든다.
5. 사람이 기획안의 증거를 클릭해 확인한다. 다른 가전 문서로 바꾸면 같은 과정을 반복한다.

예시 결과는 '건조가 약하니 개선하자'가 아니라, **어떤 상황의 어떤 잔여 작업이 기존 기능으로 해결되지 않았는지 근거를 붙인 기획 카드**다. 구체적인 콘셉트는 실제 문서 분석과 팀 검토 후 결정한다. 이 Agent가 새 가전을 물리적으로 제작해야 하는 것은 아니다.

차별성의 중심: 요약에서 끝내지 않고 **기존 기능으로 반박하는 단계와 근거가 약하면 기획을 보류하는 단계**를 넣는다. 내부 검증은 출처 일치·이미 해결된 기능 배제·가설 표시를 평가하고, 콘셉트 가치는 사람/컨설팅으로 확인한다.

## B4를 예로 보면

상황: A는 요리를 준비하고 B는 나중에 귀가해 정리한다. A가 예상보다 일찍 나가거나 B가 응답하지 않을 때도 미완료 작업이 사라지지 않아야 한다.

Agent가 사람·기기·작업 상태를 바탕으로 인계 UX와 대응 시나리오를 생성한다. 두 브라우저 역할 화면에서 담당 요청→수락→완료/보류를 실행하고, 담당 중복·아무도 맡지 않은 작업을 검사한다. 현실의 가사 분담을 자동 강요하거나 사람의 선호를 추정하지 않는다. 기획자가 정한 규칙을 사용한다.

차별성의 중심: 일반 할 일 목록이 아니라 **가전 작업 상태와 사람 작업의 연결, 인계 실패 후 복구, 이를 생성·검증하는 설계 Agent**다. 단순 공동 체크리스트만 만들면 대회 요구에 비해 약하다.

## B5를 예로 보면

상황: 사용자의 목표는 '세척기가 한 번 도는 것'보다 '다음 식사에 쓸 식기가 정리된 상태'일 수 있다. 이 목표 차이는 가설이며 인터뷰로 확인한다.

Agent가 기기 종료·사용자의 확인·정리 작업을 분리해 UX를 만든다. 입력을 '내일 아침 필요'에서 '지금 바로 필요'로 바꾸면 안내와 우선순위가 달라져야 한다. 물 잔류는 사용자가 입력하고 실제 센서로 측정했다고 표시하지 않는다. 모델별 안내가 확인되지 않으면 설명서를 확인하도록 분기한다.

차별성의 중심: 자동 세척·건조 기능과 경쟁하기보다 **사용 목적까지 일이 끝나는 경험**을 설계한다. 기계 성능 향상·에너지 절감은 실험 없이 주장하지 않는다.

## 이번 조건에서의 판단

| 후보 | 문제 근거 | 데이터 확보 | 핵심 구현 | 시연 전달력 | 남은 큰 위험 |
|---|---|---|---|---|---|
| A4 잔여수고 발굴 | 공식 문서에서 인간 작업 확인 | 현재 초기 근거 있음 | 문서 추출·대조·기획 생성 | 중간, 근거 카드 시연 필요 | 일반 RAG와의 차이·현업 가치 |
| B4 주방 인계 | 현재는 가설 비중 큼 | 합성 시나리오 가능 | 상태 흐름·예외 시뮬레이션 | 높을 가능성 | 실제 사용자 수요 |
| B5 설거지 마무리 | 공식 안내로 일부 조건 확인 | 초기 근거 있음 | 한 여정의 UX 설계 | 높을 가능성 | 사용자 목적 가설·모델별 안내 |
| A5 생활조건 공백 | 추가 조사 필요 | 모델 명세 정리가 필요 | 비교·조건 대응 | 중간 | 하드웨어 타당성 |
| B6 첫 사용 적응 | 관련 LG 활동 확인 | 설명서 사용 가능 | 안내 생성·분기 | 비교적 명료 | 기존 서비스와 중복 |

공식 배점이나 검증된 수상 확률이 아닌 내부 판단이다. **A에서 고른다면 A4, B에서 고른다면 B5 또는 B4를 먼저 논의할 가치가 있다.** 이전 B1은 일반 설계 도구에 가까웠고, 이번 후보들은 문제 영역을 더 구체화했다.

## 결정 전에 공통으로 확인할 3가지

1. 팀이 가장 설명하고 싶은 문제와 직접 관찰할 수 있는 사용자가 누구인지.
2. 어떤 후보든 모델 호출·비용·구조화 출력을 실제 확인해야 한다. 현재 모델 제공 환경은 미확인이다.
3. 후보를 고른 뒤 핵심 데모를 하나로 고정한다. 여러 후보를 합쳐 큰 플랫폼을 만드는 방향은 내일 제안서와 10/20 구현 범위를 흐리게 한다.

현재 다음 작업은 **새 후보 중 하나를 선택해 해당 후보의 구체적 제안서로 전환하는 것**이다. 기존 B1 초안을 그대로 제출하지 않는다.
