# LG 공모전 AtoZ 하네스

## 무엇이 실행하는가

이 채팅의 Codex가 실행 주체다. 사용자의 자연어 목표를 읽고 단계별 작업 패킷의 조사·생성·분석·코딩·검증 행동을 실제 도구로 수행한다. 별도의 '하네스' 키워드나 API 키가 필요하지 않다. 외부에서 상시 실행되는 봇은 아니며 대화가 끝난 뒤 혼자 진행하지 않는다.

`scripts/ax_workflow.py`가 단계 의존성, 필요한 입력, 행동 지시, 산출물 계약, 검토 기록, 증빙 버전, 다음 작업을 연결한다. 기존 `scripts/harness.py`는 공식 제출 점검과 호환성을 위해 유지한다. 두 도구의 자동 검사는 기획의 우수성을 대신 판정하지 않는다.

## 전체 흐름

목표 정렬 → 문제·경쟁 탐색 → 아이디어 발산 → 경쟁력/설계 부담 비교 → 핵심 위험 실행 → 선정 → Agent 설계 → 제안서·접수 / 구현 → 평가 → 시연·최종 제출.

| 단계 | Codex가 실제 수행할 일 | 필수 결과 |
|---|---|---|
| brief | 최신 요청과 공식 조건 정리 | 성공 기준·제약·미확인 |
| research | 웹/문서 조사, 경쟁 기능 확인 | 출처·범위·문제 영역 |
| ideate | A/B 양쪽에서 서로 다른 후보 도출 | 최소 6개, 문제·실행 흐름·어려운 부분 |
| screen | 공식 기준과 설계/검증 부담 비교 | 같은 기준의 후보 평가·탈락 이유 |
| probe | 핵심 의존성·입출력·실패 사례 실행 | 코드·입력·출력·한계 |
| select | 반대 의견까지 검토해 하나 선정 | 근거·대안·남은 위험·선정 권한 |
| design | PRD, 도구, 상태, 모델/코드 역할 설계 | 스키마·수정 루프·실패 처리·평가·백로그 |
| proposal | 공식 원고·HWP 편집·검토 | 실제 파일·팀 정보 미비 사항 |
| submission | 실제 온라인 신청 확인 | 제출본·완료 증빙 |
| build | 실제 모델과 도구를 연결해 구현 | 코드·실제 모델·통합 실행 증거 |
| evaluate | 독립 케이스와 기준선 비교 | 측정·실패·사용자 검토 한계 |
| present | 시연·발표·최종 제출 | 발표본·시연·Q&A·제출 증거 |

제안서와 구현은 설계 이후 분기할 수 있다. 팀원의 서명이 없다고 독립적인 구현까지 막지는 않는다. 권한·사용자 정보가 필요한 행동은 실제 상황에 따라 별도 처리한다.

## 자연어 요청과 진행

- “좋은 아이디어 찾아줘” → research부터 선행 조건을 확인하고 ideate/screen/probe/select까지 수행.
- “이걸 어떻게 만들지 설계해줘” → 선정된 입력을 읽고 design 패킷 수행.
- “진행해” → 저장된 상태에서 다음 가능한 단계 수행. 사용자가 지정한 범위를 넘겨 접수·메시지 등을 실행하지 않음.
- “현재 상태 알려줘” → 읽기만 수행. 보고 요청을 작업 실행으로 바꾸지 않음.
- “의논만 하자/작업하지 마” → 파일·원격 변경을 중단하고 논의.

자연어 해석은 Codex가 한다. CLI의 키워드 매칭에 맡기지 않는다. 현재 요청이 판단을 바꾸면 brief를 갱신하고 하위 결정·설계를 다시 검토한다. 이전 증거는 역사 기록으로 보존한다.

## 내부 명령

```powershell
python scripts/ax_workflow.py next
python scripts/ax_workflow.py packet design
python scripts/ax_workflow.py finish design harness/runs/current/design.json
python scripts/ax_workflow.py validate
```

`next/packet`이 다음 업무의 구체 행동·입력·결과 형식을 출력한다. Codex가 그 일을 수행해 파일을 만들고 `finish`한다. `finish`는 없는 근거, 빈 결과, 미완료 선행 단계 등을 거부하며 증빙 해시를 기록한다. 상위 단계가 변경되면 하위 완료 기록을 해제한다. 구성·요청·출처 파일이 변경되면 이전 완료 기록은 유효하지 않다.

**자동으로 확인하는 것:** 구조·선행 조건·파일 존재/버전·일부 단계의 최소 조건.
**Codex와 팀이 판단하는 것:** 근거가 주장을 실제 지지하는지, 차별성·가치·디자인 품질, 서명·접수의 진위.

## 주제 탐색의 단위

Theme A/B에서 직접 사용자·업무의 시작과 끝·산출물·재실행 계기를 먼저 정한다. 공식 포함 가능 과제는 필요한 자료·Skill·사례로 연결한다. 사용자가 항목별 목록을 요청한 경우의 12개 매핑을 영구적인 후보 구분이나 출품 규칙으로 사용하지 않는다. 전체 Agent 업무, 처음 구현할 범위, 첫 시연 사례를 각각 기록한다. 범위 변경 후에는 기존 작은 실험의 증거 범위를 다시 평가한다.

## 설계 난도와 심사 경쟁력을 함께 보는 원칙

공식 항목은 문제·인사이트·Agent 과정·구현·재사용이다. 배점은 미공개다. 여기에 모델 자유도·외부 의존성·정답 정의·실패 검사·UI 규모를 고려한다. '가장 쉬운 앱'이나 '자료가 많은 가전'만 고르지 않는다. 검증하지 않은 수상 확률·수요·절감 효과를 숫자로 만들지 않는다.

하네스 구현 완료는 참가작 완성이 아니다. 현재 채팅이 수행한 작업, 합성 규칙 실험, 실제 모델/API 실행을 결과마다 구분한다.
