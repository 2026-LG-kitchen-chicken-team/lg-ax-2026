## 단계별 작업

### 1. 공고와 제약

마감·Agent 역할·제출 양식·PC 전용 조건을 기록한다. 공고문과 상세 페이지의 차이를 정리한다. 팀원 정보 수집은 주제 조사와 병행한다.

### 2. 조사와 후보 비교

A/B 각각 최소 2개 후보를 비교한다. 자료 확보, 기존 기능 중복, 반복 실행 가능한 Skill, 10/20 구현 경로, 데모와 평가, 실패 시 범위 축소를 확인한다. 공식 근거가 사용자 불편의 빈도를 증명한다고 오해하지 않는다. 숫자 점수는 내부 판단이며 공식 배점이 아니다.

### 3. 주제 결정

추천안 1개와 대안 1개를 사용자에게 구체적으로 제시한다. 사용자 선택을 `decision.status=confirmed`, `candidate_id`, `confirmed_by`, `confirmed_at`, `rationale`에 기록한다. 근거·MVP·치명적 의존성을 점검하고 `gate topic` 실행. 결정 전 초안은 추천안으로 표시한다.

### 4. 제안서와 접수

공식 6항목 원고 → 구조도·입출력 예시 → HWP 편집 → 팀 직접 검토 → 서명·접수. 분량·서명·파일 열림은 실제 문서를 검사한 뒤 기록한다. 서류 상태를 완료로 바꿀 때 개인정보 없는 검토 기록을 증빙으로 연결한다. `gate submission` 통과가 접수 완료를 의미하지는 않는다. 실제 접수 후 별도 접수 증빙을 보관한다.

### 5. 구현

선정안 PRD → 입출력 스키마 → 최소 실행 흐름 → 평가 케이스 → UI → 통합. 모델 공급자는 하나로 시작한다. 구조화 출력·도구 호출·재시도 횟수·오류 처리·실행 로그를 구현하고, 학습용/개발용 케이스와 최종 평가 케이스를 분리한다. API 비용·지연을 측정한다. 없는 장치 기능은 생성하지 않는다.

### 6. 검증·발표·결과 제출

결과의 출처 추적, 동일 입력 재실행, 변경 입력, 누락 입력, 실패 복구, 모델 오류를 점검한다. 단순 프롬프트 기준선과 같은 조건으로 비교한다. 합성 케이스 성능과 사용자 검증 결과를 분리한다. 20쪽 이내 발표·5분 시연·질의응답을 준비하고 제출 버전을 고정한다.
