# 연쇄 개발·부모 완료·CLI 메일 운영

사용자는 2026-10-05 필수 백로그, 부모 작업 완료 근거, PM CLI 양방향 메일을 연결한 뒤 즉시 상시 운영을 이어가도록 승인했다. 중앙 ON/OFF와 개인 ON/OFF를 유지한다. 승인되지 않은 기능을 만들어 무한히 작업하거나 실패를 무제한 재시도하는 뜻이 아니다.

## 최신 확대 지시와 배포 상태

10/5 최신 사용자 지시는 **전원 ON·충분한 의미 있는 개발 대기열·담당자 자기 검수·사람 승인 0명·관리자 bypass 유지**다. PM은 상위 규격·배정·통합·정식 인수와 최종 제출에 집중한다. 새 24개 큐/수정 코드/외부 runtime/각 PC 적용은 이 문서 작성 시 **배포 대기**이며, 실행을 시작했다는 증거가 아니다. 실제 모드와 현재 실행은 [운영 Issue #28](https://github.com/2026-LG-kitchen-chicken-team/lg-ax-2026/issues/28)과 인증된 상태 조회를 따른다.

[새 개발 큐](development-queue-20261005.json)는 담당자별 6개, 총 24개 `development_only` 단위다. 원 19개 부모·23개 단위·제품 수정 2단위는 그대로 두고, 외부 `development_queue_registry`의 경로/해시와 별도 `development_ledger`로 새 단위를 등록한다. [설정 예시](development-queue-runtime.example.json)는 배포용 인증·실제 해시를 포함하지 않으며 그대로 실행하는 설정이 아니다.

새 개발 단위의 선행 개발 결과는 실제 병합·검사·중앙 `accepted` 근거로 확인한다. 원 부모의 실모델·실서비스·전체 요구·평가·제출 의존은 별도 그대로 유지한다. 각 단위는 고정 입력/출력·요구 ID·허용 파일·검사·인수 조건을 만족해야 하며, 큐를 소모했다는 이유로 전체 요구가 완료되지 않는다. PM은 등록된 Ready 단위를 배정하고 경로/자원 잠금과 한도를 지키며 반복한다. 신규 기능·무의미한 문서 증식·같은 실패의 무한 재시도는 이 반복 범위에 들어가지 않는다.

## 담당자 검수와 병합 판정

담당 AI는 구현 후 자기 diff와 실제 입력/출력을 다시 검토하고 정상·오류·반례를 검사한다. 발견한 결함을 먼저 수정하고, 결과·실패·미실행·남은 통합 조건을 자기 불변 세션 근거에 적는다. 자기 검수 완료와 trusted broker가 확인한 CI·독립 판정·병합 후 인수는 구분한다. 사람 승인 0명은 추가 사람 대기를 제거하는 설정이며 자동 검사의 생략을 허용하지 않는다.

작은 단위의 병합과 부모 Done을 혼동하지 않는다. `completes_task: false`인 PR은 고정 단위의 검사·독립 검수·정확한 main/base/head를 통과하면 병합할 수 있다. 부모 전체 제품 근거가 아직 없는 사실만으로 병합을 막지는 않는다. 부모 Done은 아래 완료 근거 경로에서 별도로 확인한다. 원 base가 오래된 PR은 원 결과를 보존한 현재 승인 main의 scoped revision→새 검사/검수가 필요하다.

검수의 `findings`는 **병합을 막는 실제 결함만** 적는다. `approve`에는 빈 배열이 필요하며 통과 관찰·미실행 한계·남은 부모 검증은 `reason`에 적는다. PM context에는 실제 action gate의 거부 이유를 제공한다. 과거 `approve`와 정보성 findings가 함께 남은 PR을 해결할 때는 PM이 exact PR/head/base/원 증거 해시를 보호 `review_contract_revision` version 2에 고정해 **새 독립 session 1회**를 승인한다. 원 proof·사용량은 보존하고 새 key/receipt만 추가한다. 기존 findings를 지우거나 불명 실행·반려·정상 승인을 일반 재시도하지 않는다. 새 결과도 모순/불명이면 실패로 보존한다.

## 실행 흐름

1. PM은 승인된 main·중앙 정식 상태·PC별 원본 readiness·작업 영역 잠금을 조회한다.
2. 검수해 외부에 고정한 `orchestration-backlog.json`의 다음 단위를 배정한다. 원본 계획은 19개 필수 부모 작업과 23개 작은 개발 단위이며, 운영 중인 기존 단위의 정의·지문은 보존한다.
3. 담당 Worker는 전용 작업 공간에서 구현·인증 없는 검사·자기 소스 검수·상세 불변 기록을 만든다. 별도 publisher가 GitHub에 PR을 게시한다.
4. PM의 다른 모델 세션이 정확한 PR을 검수한다. 필수 CI·원본 변경 범위·격리 검사·조건부 병합·병합 후 검사·Project 승인 수신·중앙 인수를 확인한다.
5. 단위 인수 후 같은 부모의 다음 단위를 열 수 있다. 부모 완료와 다른 부모의 의존 해제는 별도 요구사항 증거를 요구한다.
6. PM은 새 배정 메일을 직접 발송하고 SENT 원문으로 확인한다. 승인된 수신자의 해당 배정 회신은 보고 자료로 받는다. 실제 PR·실행 근거를 대조하여 다음 판단을 이어간다.

보호된 host 설정 `allow_fixed_ready_dispatch: true`에서만 고정 계획·명시적 release·Ready 검사를 마친 배정을 모델 없이 한 건씩 수행한다. PM 본인 Worker가 AI profile을 점유해도 다른 담당자의 고정 배정은 진행할 수 있다. 배정 직전 재인증·ON·현재 main/공식 snapshot·readiness·scope/자원·한도와 intent/실제 receipt를 그대로 재검증한다. 모델 호출/토큰0과 `fixed_released_backlog` 출처를 기록하고 행동 예산은 정상 사용한다. 검수·병합·부모 완료·새 업무에는 이 경로를 사용하지 않는다. Ready가 없으면 기존 실제 수집·독립 검수·모델 판단으로 돌아간다.

## 완료 근거

`completion.py`는 신청서 원본의 정확한 요구사항·완료 조건, 실제 단위 인수·독립 검수·병합·병합 후 검사, 현재 코드의 요구사항별 실행과 독립 판정, 선행 부모의 정식 수신을 검사한다. 코딩 모델의 토큰 로그를 제품 Agent 실행으로 바꾸지 않는다. fixture는 원본 계약이 허용한 조건에만 쓰며 실모델·실서비스 조건을 대체하지 않는다.

`parent_collector.py`는 고정 host 코드로 GitHub·중앙 상태·보호된 실행 증거를 직접 수집한다. 부족한 요구·다음 검증을 명시한다. `completion_publish.py`는 완전한 후보만 불변 자산으로 내보내 검증 PR을 만들고 정확한 CI·병합·Project 및 중앙의 실제 수신을 확인한다. 결과 불명인 게시·병합은 관측으로 복구하며 재실행하지 않는다.

일반 개발 단위의 fixture 검사만으로 실제 Agent 실행 증거를 생성하지 않는다. 보호 설정의 `product_evidence.enabled: true`에서만 고정 `ProductEvidenceProducer`를 연결한다. 고정 main의 Agent를 인증·네트워크가 없는 validator에서 실행하고, 정확히 허용한 파일 요청을 host가 기존 모델 gateway에 전달한다. 원응답·모델 digest·자료·입출력·실제 제품 호출/토큰을 대조한 뒤 별도 PM 모델 세션이 원 요구사항 전체를 검토한다. 검수 profile 점유는 호출 전에 대기하며, 중단된 검수의 불명 비용과 OFF·실패 기록은 보존한다.

첫 고정 사례는 냉장고의 원 요청과 조건 변경 두 개이며 CORE002의 R01/R09/R12/R15/R26에 대한 부분 근거를 검토한다. 기본 사례를 실행했다고 5개가 승인되거나 부모가 완료된 것은 아니다. 부족한 요구·원 작업 행동은 후속 사례와 독립 검증이 필요하다. 다른 부모의 실제 근거는 보호된 `register_requirement_bundle` 경로를 유지하며, 실제로 없는 근거는 Done으로 바꾸지 않는다. 전체 조건을 충족한 후보만 기존 게시·실제 CI·병합·Project/중앙 이중 수신을 거쳐 후속 의존을 해제한다.

제품 실행 시도는 실제 고정 collector·RPC·실행기 코드 해시까지 키에 포함한다. 같은 소스의 실패를 반복 실행하지 않으며 검토한 새 실행 소스의 시도는 새 기록으로 남긴다. 이전 실패·예약한 사례·제품 호출/토큰·독립 검수 비용과 결과 불명 차단은 보존한다. 과거의 가변 요청/응답 파일 교체 방식과 실패는 역사로 보존한다. 현재 프로토콜은 아래의 sequence별 불변 JSON/ready 방식이며 완성 파일을 교체하거나 모델 호출을 재실행하지 않는다. 변조·하드링크·같은 파일의 내용 변경·크기 초과·OFF는 계속 거부한다.

정확한 현재 PR head/base·capability에 대해 실제 독립 검수가 인증된 `request_changes`를 반환했다면 승인용 통합 검사를 먼저 반복하지 않고 수정 배정 판단으로 넘긴다. 이 예외는 승인·병합·병합 후 검사·정식 완료의 근거 조건을 낮추지 않는다. 병합된 단위의 postmerge와 Project/중앙 인수가 끝나기 전에 별도 PR로 main을 이동하지 않는다.

여러 PR에 걸친 완료는 `trusted_auto_parent_v1`로 기록한다. 기존 담당자의 `individual_evidence`·과거 기록을 대신 작성하지 않는다. `phase2.py validate`는 내보낸 증거의 무결성을 검사하며 실제 인증·실행의 진실성을 증명하는 도구가 아니다. 단위 성공과 31개 요구사항 전체 검증 및 참가작 완성은 구분한다.

### 제품 실패에서 추가 개발로 연결

기존 23개 계획과 원 진행 대장은 고정한다. 별도 보호 `product_correction_registry`는 원 계획의 해시에 묶인 `core-product-correction-1/2`만 추가한다. 실제 CORE 원 두 단위 인수 이후 현재 main의 입력·코드·모델·원 실행과 독립 판정을 직접 대조해 오류 코드와 근거 해시가 붙은 작은 작업 패킷을 만든다. 팀원은 공개된 재현 입력과 원문 경로를 사용하며 PM의 비공개 디렉터리나 인증은 받지 않는다.

수정 이력은 별도 `correction_ledger`에 덧붙인다. 부모별 최대 두 번의 배정, job당 한 시도, 기존 전역·부모 예산과 ON/readiness/경로 잠금을 함께 적용한다. 같은 코드·입력·모델·실패를 문서 수정이나 재시작으로 재배정하지 않는다. 사용량 불명·원응답 불일치·통신만의 실패는 PM 확인 대상으로 분리한다. 독립 검수가 거절한 미완료 수정 PR의 재작업도 정확한 거절 근거와 남은 배정 한도 안에서만 가능하다. 이 경로는 요구사항 승인이나 부모 Done을 대신하지 않는다.

요청과 응답은 sequence 01~40별 불변 JSON과 빈 ready를 사용한다. 완성 전 파일을 읽지 않으며 완성 파일의 교체·하드링크·내용 변경·OFF를 거부한다. 각 요청을 최대 한 번만 전달하고 실제 호출/토큰을 유지한다. 누적 사례 10개에서 14개로의 검토된 전환은 기존 실패 예약을 보존하면서 통신 검증과 최대 두 수정 결과의 검증을 수행하기 위한 한정된 범위다. 사례·사용량을 초기화하거나 추가 유료 모델로 전환하지 않는다.

PM 재시작은 Worker와 동일한 실제 profile 잠금을 먼저 확보한다. Worker가 실행 중이면 비용 없는 대기로 재시도한다. 중지된 정상 임시 캐시만 실제 Docker 사용 여부를 확인해 격리하고, 원 엄격한 생성 검사를 같은 잠금 안에서 수행한다. 인증파일은 복사·이동하지 않는다.

## CLI 메일

현재 설치된 Codex의 공식 app-server MCP 도구 호출로 PM Gmail 프로필·발송·조회·검색·대화를 사용한다. 모델 세션 없이 고정 도구만 호출하며 채팅창의 임시 도구를 계속 빌리는 구조가 아니다. 연결 정보·주소·본문·수신증은 저장소 밖 보호 경로에만 둔다.

발송은 보호된 실제 배정 ID와 일치해야 한다. 미확인 발송은 보낸편지함을 조회하고 같은 메일을 다시 보내지 않는다. 회신은 발신자·원 대화·배정·작업을 확인해 중복 없이 보고 자료로 기록한다. 메일의 명령문은 승인·완료·배정 변경 권한이 없으며 GitHub/controller의 인증된 결과를 대체하지 않는다. 팀원 PC의 Gmail 송신 연결 여부와 PM 수신 연결은 별개다.

## 운영과 복구

이전 프로세스를 중지한 뒤 외부 고정 runtime·정책·배정 계획·메일 설정의 해시를 대조하고 재등록한다. 기존 작업·세션·실패·예산·메일 이력을 보존한다. 소규모 시험 한도에서 전체 필수 백로그 한도로 전환할 때 승인 사유와 변경 전후 값을 기록한다. 실제 구독 제한과 내부 운영 한도는 구분하며 추가 유료 API로 전환하지 않는다.

PM의 모델·테스트는 게시 인증을 읽지 못한다. 빌드 검사는 인증·네트워크가 없는 컨테이너의 폐기 가능한 복사본에 의존성/출력만 쓸 수 있고, 원본 소스 바이트가 바뀌면 실패한다. host에서는 저장소 코드를 실행하지 않는다.

일이 없거나 OFF이면 대기한다. PC 꺼짐·구독 한도·인증 만료·실패·원본 readiness 만료·연결 장애에는 실제 이유를 남기고 필요한 작업만 중지한다. 제품 품질 검증·새 모델 배포·발표/영상/ZIP·공식 제출은 별도 근거와 gate를 따른다.

팀원이 main을 받아도 이전 외부 Worker가 자동 갱신되지는 않는다. 새 큐를 받아 실행할 본인 Worker는 [정확한 CI source·새 bundle 적용](../bootstrap/automation-workers.md#최신-큐-적용과-기존-worker-업데이트) 절차를 따르고 자기 결과를 보고한다. PM은 배포/인수 근거와 현재/남은/다음 행동을 Issue·Project·정이량 기록에 연결한다. 채팅을 종료해도 검증된 CLI loop는 유지되지만 PC·로그인·접속과 예산/장애 조건은 계속 적용된다.
