# PM 수동 회수: API 실패 계약

- 기록 ID: `PM-MANUAL-API-RECOVERY-20261005`
- 담당: 정이량 / `jeongiryang`
- 수행 AI: Codex PM 작업의 독립 진단·회수 담당 Agent
- 관련: 개발 Issue #121, 운영 Issue #28, `P2-PM-003`, `dev-pm-api-run-failure-contract`
- 재개 상태: 원 Worker 작업은 blocked이며, 이 별도 수동 회수 변경은 PM 검수와 실제 PR·CI·통합 확인을 기다린다.

## 지시와 해석

사용자는 네 담당자의 자동화를 켜고 의미 있는 개발 작업을 계속 진행하도록 지시했다. PM은 이번 실행이 게시 전에 차단된 원인을 조사하고, 이미 생성된 API 실패 계약 구현을 추가 모델 호출 없이 별도 작업 공간으로 회수하도록 지시했다. 원 실행의 blocked·halt·사용량·검사·출력은 보존하고, 실제 비밀정보 탐지 규칙은 유지한다.

AI는 이를 기존 terminal 작업을 다시 실행하거나 승인하는 지시로 해석하지 않았다. 원 코드와 검사 증거를 고정한 뒤, 합성 유출 테스트 문자열의 소스 표현만 수정하고 새 PM 수동 검수 대상으로 제공하는 작업으로 해석했다.

## 실제 진단과 수행

원 작업 `auto-5b3f96ede19a1c0e89369a7be13740a18b57b51c` attempt 1은 모델 exit 0, 고정 검사 2개 exit 0을 기록했다. 이후 소스 게시 검사의 Bearer 형태 탐지에 걸려 blocked·halt_worker=true가 되었고, controller는 blocked 보고를 수락했다. 게시 수신증이나 PR/head는 생성되지 않았다.

탐지 위치는 새 `tests/test_api_run_failure_contract.py`의 module-level `SECRET` 합성 상수다. 이 상수는 가짜 runner 오류·보관된 실패 레코드·공개 응답의 제거 여부를 검사하는 테스트 입력이다. 해당 문자열이나 실제 인증 값은 문서에 복사하지 않았다.

원 base `7652048327d8bf20410af14e6f78979b8f721d63`의 별도 `codex/manual-pm-api-recovery-20261005` 작업 공간에서 구현 파일 2개와 원 담당자 세션 문서 2개를 정확한 허용 영역으로 회수했다. 합성 상수의 할당은 실행 시 문자열 조합으로 표현했다. AST 검사는 수정 전후 실행 시 상수 값이 같고, 나머지 생성 소스 바이트가 같으며, 게시 탐지 패턴이 수정 소스에 남지 않는 것을 확인했다.

## 사용량과 완료 판단

원 Codex 실행은 입력 1,185,931 토큰(캐시 입력 1,079,552 포함), 출력 15,027 토큰, 합계 1,200,958 토큰이다. 캐시 사용량은 합계에 다시 더하지 않는다. 이번 회수에는 추가 모델 호출이 없다. 원 비용·대장·예약·blocked·halt·원 출력은 보존한다.

새 고정 검사는 인증 정보를 마운트하지 않고 네트워크를 차단한 validator 컨테이너에서 수행한다. 정확한 명령·결과·소스 해시는 아래 근거 기록에 연결한다. 검사 통과만으로 원 자동 작업의 게시·승인이나 부모 `P2-PM-003`의 최종 완료를 기록하지 않는다.

## 다음 행동과 PM 요청
