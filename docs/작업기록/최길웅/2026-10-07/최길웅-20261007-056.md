## 2. 해석(AI 해석)
- 사용자가 P0 확정을 기다리지 말고 웹 쪽 view-model과 화면 부품을 먼저 만들라고 직접 지시했다. PM 답은 아직 없으므로 이 결정이 사용자 지시라는 점을 기록한다.
- 필드 이름은 #234에 제안한 WEB 안을 쓴다:
  - Concept: `target_user`, `usage_context`, `before_steps`/`after_steps`(각 단계 `text`, `basis`(observed/inferred), `evidence_ids`), `mechanism`(`summary`, `feature_ids`, `conditions`)
  - Need/Gap: `counter_evidence_ids`
  - 이 필드를 읽는 곳은 어댑터 한 파일뿐이다. P0에서 이름이 바뀌면 그 파일만 고친다.
- 현재 계약은 Concept·Need·Gap에 추가 필드를 허용하지 않는다(`additionalProperties: false`). 따라서 지금의 실제 실행 기록에서는 새 영역이 항상 '미제공'으로 나온다. 화면에서 값을 만들어 넣지 않는다.
- 제품 fixture에 장면 값을 넣지 않는다. 하드코딩한 기획을 시연하지 않기 위해서다. 채워진 상태는 단위 테스트(손으로 만든 객체)로만 확인한다.

## 3. 수행과 결과
- **`apps/web/src/planningScenes.ts`(view-model 어댑터):**
  - 필드마다 `not_provided` / `malformed`(사유) / `ok` 세 상태로 나눈다.
  - 관찰(observed) 단계에 근거가 없으면 형식 불일치로 처리한다. 자료에 없는 근거 ID는 '원문 없음'으로 표시한다.
  - 반대 사례는 콘셉트가 다루는 Gap과 그 Need에서만 읽는다. 필드가 있고 비어 있으면 '반대 사례 없음(코어 기록)', 필드가 없으면 '미제공'으로 구분한다. 같은 근거가 지지 근거로도 쓰였으면 경고한다.
- **`apps/web/src/ConceptScenes.tsx`(컴포넌트):** 대상 사용자·사용 상황, 개선 전/후 단계(관찰 근거/추정 배지와 원문 칩), 작동 방식(연결 기능 이름·조건), 반대 사례를 보여 준다.
  - 아무것도 기록되지 않았으면 한 줄 안내만 표시한다: "이 실행 기록에는 없습니다 … 화면에서 만들어 넣지 않습니다".
  - 형식이 틀린 필드는 사유만 보이고 내용은 숨긴다.
  - 근거 칩은 기존 `Refs`를 그대로 넘겨받는다. 그래서 원문 보기 방식이 다른 화면과 같다.
- **연결:** `PlanningViews.tsx`의 후보 상세 검토(REVIEW) 패널 맨 위에 넣었다. CSS는 `planning.css`에 추가했고, 좁은 화면에서는 한 열로 바뀐다.
  - 파일 이름은 Windows의 대소문자 구분 없는 경로 충돌(`ConceptScenes.tsx`와 `conceptScenes.ts`)을 피하려고 `planningScenes.ts`로 정했다.
