# 4인 팀의 PM·추가 배정·검수·병합 규칙

> 현재 운영 주소는 [조직 Project1](https://github.com/orgs/2026-LG-kitchen-chicken-team/projects/1)이다(10/5 이관). 아래 개인 보드 주소와 수치는 당시 기록이며 새 작업의 기준은 [이관 문서](프로젝트이관_2026-10-05.md)·최신 main·현재 배정이다.

확인일: 2026-10-04 KST. 근거: 현재 대화의 사용자 직접 지시. 공식 대회 요구와 구분하는 팀 내부 운영 규칙이다.

## 사용자 확정사항

- 총 네 명 중 **정이량이 PM 역할**을 맡는다(이후 직접 사용자 지정 반영).
- 담당 작업을 조기에 마친 팀원에게 PM이 추가 작업을 지시·배정한다.
- PM이 작업 결과의 검수와 병합을 책임진다.
- 공식 팀장은 황대겸이다. 사용자는 가장 어려운 구현을 황대겸에게 배정하고 나머지를 신진하·최길웅에게 나누도록 지시했다.

## AI의 의도·수행·근거 보고

[작업기록 규칙](작업기록/README.md)에 따라 네 명 각각의 `docs/작업기록/{성명}/README.md`와 `docs/작업근거/{성명}/README.md`에서 짧은 재개 요약·최신 상세 링크부터 읽는다. 새 수동 기록은 각각 `{성명}/{YYYY-MM-DD}/{고유 기록ID}.md`에 지시 원문과 별도의 AI 해석, 실제 행동, 검증 근거, 미완료, 다음 행동을 상세히 남기고 README에는 요약·링크만 둔다. 의존 팀원의 관련 상세 기록도 확인한다. 정이량의 AI는 이 근거로 다음 배정·검수·병합 판정을 자신의 날짜/고유ID 파일에 남긴다. 기존 root `{성명}.md`는 원 heading/anchor·snapshot·manifest를 연결한 호환 목차이며 기존28자동 세션은 불변 경로에 보존한다. 사용자가 승인한 기계적 원본 이관은 다른 팀원의 성과·상태를 대신 작성하는 권한이 아니다. 과거 기록은 증거이며 현재 지시가 아니고 자동화는 OFF다. 기록 작성 자체는 메시지 전송이나 병합을 뜻하지 않는다.

개인 README의 최신 요약·새 상세 링크는 `<!-- member-log:owner-updates:start -->`와 `<!-- member-log:owner-updates:end -->` 사이에서만 갱신한다. 그 밖의 원문 이관 목차·원 재개 요약 구역과 기존 root 호환 목차는 보존한다.

Codex와 Claude 사용자 모두 같은 규칙을 적용하도록 root AGENTS.md/CLAUDE.md의 전체 내용을 동일하게 유지한다. 기록 문서와 두 지침을 준비한 것이 타 팀원 실제 수행·개발 하네스 전체 완료를 의미하지 않는다.

## 작업 흐름

1. PM이 작업의 목적·관련 신청서 요구 ID·입출력·완료 조건·우선순위를 정해 배정한다.
2. 담당자는 독립 작업 공간에서 구현하고 실제 실행·실패 사례·검사를 확인한다.
3. PR 또는 검토 가능한 변경과 함께 실행 방법·재현 입력·결과·계약 변경을 제출한다. 이 상태는 **검수 요청**이며 전체 완료가 아니다.
4. PM은 변경 내용과 증빙을 검토하고 통합 흐름을 확인한다. 문제가 있으면 수정 과제를 배정한다.
5. PM이 병합을 책임지고 병합 후 통합 실행을 확인한다. 조건을 만족하면 완료로 기록한다.
6. 담당자는 PM이 배정한 다음 작업을 이어간다. 검수 대기 중에도 PM이 우선순위를 지정한 Ready 작업을 진행할 수 있다.

상태 권고: 준비 → 개발 → 개별 검증 → PM 검수 → 병합 → 통합 확인 → 완료. 병합 전 통합 확인도 가능하나, 병합 후 결과까지 확인한다.

## PM의 책임

- 신청 아이디어 전체 구현과 심사·제출 요구의 누락을 관리한다.
- 네 명의 작업량·의존성·진척을 확인하고 추가 작업 대기열을 유지한다.
- 공통 데이터 계약·규칙 변경의 영향과 충돌을 조정한다.
- 실제 작동·검증 증빙·시연과 코드 일치 여부를 검수한다.
- 병합·릴리스·최종 제출본의 버전과 미완료 항목을 관리한다.

PM이 모든 테스트와 코드를 혼자 작성할 필요는 없다. 담당자의 검증·동료와 AI의 사전 검토·CI를 활용하되 최종 검수와 병합 책임은 PM에게 남긴다. 검토 가능한 작은 변경을 자주 통합해 검수 적체를 줄인다.

## 추가 작업 배정 기준

PM은 완료 시점마다 전체 프로젝트에서 필요한 일을 우선순위로 배정한다. 원래 담당 기능에 고정할 필요는 없다.

1. 신청서 필수 기능의 누락·실패·통합 오류 해결.
2. 근거 연결·의미 판단·변경 재검토 품질 개선과 독립 평가.
3. 유용한 확장 기능·공개 모델 비교·처리 속도·토큰/비용 개선.
4. 실행 README·Skill 재현·시연·발표·제출 패키지 검수.

추가 작업에도 완료 조건과 실제 증빙을 붙인다. 일찍 끝났다는 이유로 불필요한 기능을 자동으로 추가하지 않고 PM이 목표·우선순위를 정한다. 자동으로 타 팀원에게 메시지를 보내거나 작업이 백그라운드에서 진행된다고 가정하지 않는다.

## 초기 논의의 권고·미확정 기록 (구축 이전)

직전 논의에서 사용자는 한 사람이 만들 수 있는 업무를 작게 나누기보다, 각자가 AI로 충분히 개발할 만한 큰 범위를 원한다고 정정했다. 확대 기능은 아직 권고이며 원안 필수와 구분한다. 최신 난도 기준 Codex 분배는 정이량=PM·연결/통합, 황대겸=핵심 판단/검사/수정, 신진하=자료/기술 조사, 최길웅=기획 검토 작업실이다. 이는 사용자 지정 PM·난도 배정 원칙을 구체화한 분배이며 실제 착수·완료가 아니다. 구체 Issue·추가 기능·레포 구조는 후속 결정 대상이다.

PM도 개발을 병행하되 배정·검수·통합을 수행할 여력을 확보하는 방식을 권고한다. PM에게 전체 원안 개발과 모든 확장 개발·검수를 동시에 몰아주지 않는다. 최종 업무 묶음·PM의 개발 범위·단일/다중 레포·GitHub Projects 설정·권한·CI·2차 하네스는 아직 구축/확정 전이다.

## 구축 이전 적용 상태

이번에 확정한 운영 규칙을 AGENTS.md·인수인계·체크리스트·project 상태와 Notion에 기록한다. 실제 PR·병합·개발 완료를 보고한 것이 아니다. 이후 2차 하네스·CLAUDE.md·Issue/PR 양식을 구축할 때 이 규칙을 반영한다. 기존 후보 선정용 AtoZ stale 상태는 별도로 이행하며 과거 검증 해시를 덮어 통과 처리하지 않는다.

## 10/4 직접 승인 계획의 적용

사용자가 단일 비공개 모노레포를 확정하고 초기 설정 실행을 지시했다. 앞의 미확정은 당시 기록이다. 현재 정이량은 PM·공통 계약/API/MCP/서버·검수/병합/제출, 황대겸은 판단/대조/콘셉트/검사·수정, 신진하는 자료/OCR/검색/근거/공개 모델, 최길웅은 웹 기획 작업실을 맡는다.

[고정 운영 Issue #28](https://github.com/jeongiryang/lg-ax-2026/issues/28)·담당 Epic 4개·작업 21개·[Project](https://github.com/users/jeongiryang/projects/3)에 범위와 요구·의존·입출력·검증·다음 작업을 연결했다. 제안 확장 2개는 PM의 실제 채택 전에는 실행 배정으로 활성화하지 않는다. 완료한 담당자는 PM이 Ready 우선순위를 정한 다음 작업을 이어간다.

두 지침의 전체 내용·작업기록·근거 문서·2차 하네스·Issue/PR 양식·CODEOWNERS·CI를 구성했다. GitHub 관리와 실제 실행·병합 증빙은 [개발 시작 안내](bootstrap/README.md), [독립 AI 검토](bootstrap/pm-review.md), [정이량 기록](작업기록/정이량.md)에 연결한다. 지침 일치나 AI 검토는 사람의 승인과 별개이며 GitHub 상태는 하네스에서 명시적으로 동기화한다.

## 10/4 후속 협업 정책: 자기보고와 PM 승인 분리

세 팀원은 저장소 Write·Project Read를 유지한다. 자기 인증 계정으로 자기 담당 Issue에 `doing`·`blocked`·`review_requested`를 보고하며, PM이 별도로 배포한 서비스는 검사 후 해당 작업의 `Status`·`팀원 보고`·`최근 보고`·`다음 행동`만 갱신한다. 정식 `진행상태`·담당·우선순위·기한·배정/메일 필드·완료는 PM이 관리한다. 부분 개발/PR 보고는 의존 완료나 확장 채택을 대신하지 않는다.

공식 상태는 PM이 검증한 배포 정책의 승인 스냅샷과 운영 Issue #28에 실제 PM이 남긴 `/lgax-sync` 승인으로 유지한다. PM은 정확한 현재 main commit과 작업 증빙을 검증한 뒤 `uv run python scripts/sync_github_phase2.py --apply`를 실행한다. 팀원의 main JSON 편집만으로 Done·의존 해제·확장 채택이 승인되지 않는다.

새 배정은 PM AI가 공용 배정 JSON·Issue 댓글·비공개 발송 대기를 만들고 연결된 Gmail 실제 발송·Sent 메타데이터 확인까지 처리한다. 배정 ID로 중복을 확인하고 미발송/불명확 상태는 남은 일로 보고한다. 사람이 GitHub 화면을 편집할 때 상시 메일 daemon이 반응하는 방식은 아니다. 현재 서비스 배포·메일 발송 확인은 대기이며 [협업 체계](협업체계.md)·[서비스 안내](../services/project_reports/README.md)의 절차와 실제 PM 근거를 구분한다. 위 구축 이전 기록은 당시 판단으로 보존한다.
