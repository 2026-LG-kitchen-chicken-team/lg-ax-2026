## 1. 어떤 아이디어이며 누구의 업무인가

상대 제품은 **정수기 구독 사업 운영·분석 담당자가 숫자와 시장 자료를 함께 검토하는 작업실**로 해석된다. 실제 사용자 인터뷰로 확인된 타깃은 아니며 데이터 항목과 화면·기획서에 근거한 추론이다. 구독 소비자가 자신의 청구서를 관리하는 앱이나 정수기를 직접 제어하는 서비스와는 다르다.

기획서의 중심 문제는 내부 신규·해지·만기 집계만으로 실적 변화를 설명하기 어렵다는 것이다. 과거 변화의 분해, 다음 실적 예측, 외부 시장 관측을 모아 설명 보고서를 만들려는 방향이다. 다만 6/20 종합 문서는 세 구성 요소를 구상안이라고 명시한다. [종합 구상 문서](https://github.com/B23en/water-purifier-subscription-management-system/blob/a498b7dae28f09bf8d1c6f7a34013435af80f88c/docs/spec_summary.docx).

코드가 지원하는 흐름을 설명하는 예시이며, 이번 조사에서 직접 실행한 대화가 아니다. 자연어 parser는 한 번에 자료 종류/화면 하나를 선택한다. 시장동향은 챗봇의 화면 enum에 없어 수동 탭 선택과 구분한다.

| 업무 질문 예시 | 연결되는 기능 | 실제로 보여주려는 것 |
|---|---|---|
| 최근 6개월 신규 가입을 판매 채널별로 봐줘 | 기간·신규·채널 화면 선택 | 월별/채널별 집계와 차트 |
| 지난달 신규 감소 원인을 봐줘 | 신규 증감 대시보드 | 서비스 주기·관리 방식·채널별 MoM/YoY 변화; 인과 원인 입증은 아님 |
| 다음 달 신규를 예측해줘 / 다음 달 해지를 예측해줘 | 각각 별도 질문으로 예측 대시보드 | 다음 달 예측값·모델 비교·오차 기반 구간 |
| 시장동향 탭→수집 버튼 또는 기존 결과 조회 | 수동 선택하는 시장 자료 화면 | 뉴스·블로그 요약과 쇼핑 가격 관측 |

## 2. 실제 구조와 LLM의 역할

```text
CSV/TXT 업무 자료
  → 모델·채널 분류/정규화
  → 연도별 Parquet·월별 요약·누적 집계
  → 실적/예측/증감 계산
  → Streamlit 표·차트

자연어 질문
  → OpenAI/Azure LLM 또는 키워드 fallback
  → 자료 종류·화면·조회 기간의 JSON
  → Streamlit 화면 상태 변경

네이버 뉴스·블로그·쇼핑
  → API/본문 수집·원본/해시 저장
  → 문서별 LLM 요약·관련성 판단
  → DuckDB·시장 context JSON
  → 시장동향 화면/향후 보고서 생성 입력
```

### 데이터 가공·화면

`AccountUpdate.py`는 원천 CSV/TXT를 정리하고 모델·판매 채널 등 분류를 적용한다. 모르는 제품 모델은 사람이 분류를 보완하는 경로가 있다. `DB_Updater.py`, `SummaryDB_Builder.py`, `CumulativeDB_Builder.py`가 저장·요약·누적을 담당한다. `app.py`는 데이터 처리와 대시보드 모듈을 연결한다. [앱 진입점](https://github.com/B23en/water-purifier-subscription-management-system/blob/a498b7dae28f09bf8d1c6f7a34013435af80f88c/PythonCode/app.py), [가공 코드](https://github.com/B23en/water-purifier-subscription-management-system/blob/a498b7dae28f09bf8d1c6f7a34013435af80f88c/PythonCode/AccountUpdate.py).

### 자연어 챗봇

`llm_parser.py`의 기본 모델은 `gpt-4o-mini`다. OpenAI 클라이언트를 우선 선택하고 키가 없거나 클라이언트 생성에 실패하면 Azure를 선택한다. 실제 모델 호출/파싱 실패 때는 키워드 fallback으로 가며 Azure 자동 재호출이라고 해석하지 않는다. 질문을 `data_type`, `dashboard`, `start_month`, `end_month` 등으로 구조화하고 `intent_router.py`가 화면에 적용한다. 날짜·상대 기간과 예측/증감 키워드 보정도 있다. **현재 확인되는 역할은 자연어로 분석 화면을 조작하는 라우터다.** 목표를 나눠 도구를 반복 선택하고 산출물을 검사·수정하는 전체 자율 업무 Agent는 이 경로에서 확인되지 않는다. [LLM 파서](https://github.com/B23en/water-purifier-subscription-management-system/blob/a498b7dae28f09bf8d1c6f7a34013435af80f88c/PythonCode/chatbot/llm_parser.py), [화면 라우터](https://github.com/B23en/water-purifier-subscription-management-system/blob/a498b7dae28f09bf8d1c6f7a34013435af80f88c/PythonCode/chatbot/intent_router.py).

이 구조도 단순 자유 답변과는 다르다. 숫자는 Python 모듈이 계산하고 LLM은 사용자 요청을 화면/기간 조건으로 바꾼다. 우리도 LLM에게 모든 검증을 말로 맡기기보다 ID·버전·인용·개수·수정 횟수 같은 검사를 코드로 확실히 해야 한다.

### 증감 분석

`models/segment_shap`라는 이름이 남아 있지만 **현재 구현을 SHAP 기반 AI 설명으로 부르면 잘못이다.** 기존 ML/SHAP/STL 실험 코드는 현재 트리에서 제거됐고 운영 증감 분석은 직접 집계 방식이다. 항목별 월간·연간 차이, 절대 변화 비중, 전체 변화와의 상관을 계산한다. 결과는 어디에서 변화가 컸는지의 설명 통계다. 왜 변했는지의 인과관계가 입증되는 것은 아니다. 역사 보고서는 STL 신호도 기록하므로 과거 실험 전체가 무가치했다고 해석하지 않는다. [현재 계산](https://github.com/B23en/water-purifier-subscription-management-system/blob/a498b7dae28f09bf8d1c6f7a34013435af80f88c/models/segment_shap/segment_contribution.py), [전환 PR5](https://github.com/B23en/water-purifier-subscription-management-system/pull/5).

### 시장 자료 수집과 요약

활성 소스는 네이버 뉴스·블로그·쇼핑이다. 원문·URL·수집 시각·내용 해시를 저장하고 LLM이 요약·근거 구절·제품명·관련성 등을 구조화한다. `doc_id+content_hash+model_name+prompt_version`으로 같은 내용을 재요약하지 않는 캐시 설계가 있다. 출처/버전과 비용 관리 측면에서 참고할 만하다. 코드 기본 모델과 문서의 운영 설정이 다를 수 있고 실제 호출 모델은 공개 로그로 확인하지 않았다. [시장 자료 명세](https://github.com/B23en/water-purifier-subscription-management-system/blob/a498b7dae28f09bf8d1c6f7a34013435af80f88c/docs/webcrawler_report_context_spec.md), [요약 코드](https://github.com/B23en/water-purifier-subscription-management-system/blob/a498b7dae28f09bf8d1c6f7a34013435af80f88c/PythonCode/WebCrawler/summarizer.py).

최종 export는 **보고서 생성 LLM에 넣을 시장 관측 JSON**이다. 예측·증감·시장 자료를 통합한 최종 자동 보고서 Agent와 그 검사/수정 반복까지 구현됐다고 확인할 수 없다. 같은 화면에 여러 기능이 있다는 것과 하나의 요청으로 전체 업무가 자동 완주한다는 것은 다르다. MCP나 ChatGPT/Claude 플러그인 호스트 어댑터도 확인한 공개 트리에는 없다.

## 3. 어디까지 만들어졌으며 무엇이 미확인인가

| 코드/문서에서 확인한 것 | 실행·성과로 확인하지 못한 것 |
|---|---|
| 데이터 가공·집계·대시보드 연결 | 실제 사내 자료의 출처·사용 권한·대표성 |
| 예측 함수·비교·백테스트 계산 | 이번 조사에서 재현한 예측값·성능 |
| 증감 계산과 UI 연결 | 변화의 원인·해지율 개선 |
| 시장 수집·요약·context export | 정기 운영·최종 보고 Agent의 자동 완주 |
| 모듈별 PR·방법 변경 보고서 | 실제 업무 사용·시간 절감·사용자 검토 결과 |

문서의 실험 수치는 개발팀 자체 보고다. 예측 보고서는 신규/해지/재구독률 MAPE를 10.5%/8.2%/11.3%로 기록하고 대응 naive를 10.8%/9.5%/11.7%로 제시한다. **어떤 모델도 naive를 통계적으로 유의하게 능가하지 못했다고 문서 자체가 명시한다.** 비교 실험을 했다는 강점은 있지만 검증된 예측 우위라고 표현할 수 없다. 원천 자료·시점별 예측 출력·실행 로그가 공개돼 있지 않아 이번 조사에서 수치를 독립 재현하지 않았다. [예측 보고서](https://github.com/B23en/water-purifier-subscription-management-system/blob/a498b7dae28f09bf8d1c6f7a34013435af80f88c/docs/예측모델개발1차보고서.pdf), [백테스트 코드](https://github.com/B23en/water-purifier-subscription-management-system/blob/a498b7dae28f09bf8d1c6f7a34013435af80f88c/models/forecast/test_backtest.py).

SHAP/STL 보고서에도 대부분 0 부근/음수인 R²와 실패 원인을 남겨 직접 기여도 방식으로 바꿨다. **실패한 ML을 계속 포장하지 않고 실제 결과에 따라 단순한 계산을 선택한 점은 배울 부분**이다. 우리 공개 모델 탐색도 모델 크기나 GPU 사용량보다 같은 평가셋에서의 실제 결과로 선택해야 한다. [방법 변경 보고서](https://github.com/B23en/water-purifier-subscription-management-system/blob/a498b7dae28f09bf8d1c6f7a34013435af80f88c/docs/분석%20방법론%20변경%20보고서%20김민재.docx).

### 정적 대조에서 찾은 주의점

1. 여러 범주의 주변집계가 겹치므로 채널 감소·방문관리 감소·주기 감소를 합하거나, 교차 집계 없이 특정 교차 고객군이 원인이라고 확정할 수 없다. 해지 건수만으로 위험집단 분모가 필요한 해지율 상승도 입증되지 않는다.
2. 구상서·초기 보고서·현재 코드의 범위와 운영 방법이 다르다. 여러 달 예측/분기별 단일 모델 계획과 현재 다음 달/Top3 비교를 구분해야 한다. 초기 SHAP/STL 기능은 현재 트리에서 재현할 수 없다. 증감 코드의 상관0.5는 분석 대상 필터, 상관0.7/비중20%는 강조 기준이므로 두 값 자체를 문서/코드 불일치로 판단하지 않는다.
3. SHAP 문서의 데이터 범위가 2026.07까지인데 최초 commit은 6/22이고, 내장 그래프의 끝부분에 거의 0인 관측이 있다. 부분월·미완성 자료 여부는 미확인이다. 예측 로더는 따로 직전 완전월만 쓰므로 두 보고서의 계절성 결론을 같은 조건의 결과로 합치면 안 된다. 이것만으로 자료 조작을 추정하지 않는다.
4. root 설치 목록 외에 예측/크롤러 별도 의존성이 있고 DuckDB 버전도 다르다. `app.py`는 import 예외를 모두 '구현 전' 안내로 바꿔 의존성 오류와 실제 미구현을 구별하기 어렵다.
5. 데이터·카테고리 CSV·DB·예측 결과 대부분은 `.gitkeep` 또는 추적 제외이며 공개 샘플 완주팩이 없다. 자료를 비공개로 두는 이유와 별개로 외부 재실행은 어렵다. `PythonCode/test.py`도 일반 시험 suite가 아니라 CSV→Parquet 변환 코드다.

위 사항은 경쟁작을 깎아내릴 근거가 아니라 **우리도 제출 전 문서/코드/영상 일치·부분월/버전·지표 정의·재실행을 확인해야 한다는 교훈**이다. 내부 검증이나 비공개 최신 작업이 없다고 단정하지 않는다.

## 6. 우리가 대비할 핵심

### 우선1 — 실제 기획 업무를 완주

황대겸의 핵심 판단 계약/불편 대조/콘셉트/검사·수정, 신진하의 모델·버전별 자료팩, 최길웅의 실제 후보 검토 화면, 정이량의 웹/MCP/Skill 통합이 첫 목표다. 기존 역할·Issue를 따르며 이번 조사로 별도 배정을 발송하지 않는다.

그쪽은 이미 계산과 화면을 이어 붙였다. 우리는 설정·하네스 설명에 많은 발표 시간을 쓰고 결과 화면이 미구현이면 불리하다. **최소1요청이 끝까지 실제 실행되는 첫 인수물을 빨리 연결하고, 이후 세 제품과 오류 사례로 넓히는 순서**가 적절하다. 하네스 추가 기능보다 참가작 코어·자료 인수를 우선한다.

### 우선2 — 일반 LLM과의 차이를 검증

MCP는 사용 채널/연결 규격이지 판단 품질의 증거가 아니다. 좋은 LLM에 같은 리뷰·설명서를 주면 불편 요약과 아이디어는 생성할 수 있다. 우리는 다음을 **동일 입력의 일반 LLM과 실제 비교**해야 한다.

- 원문 문장·페이지/위치·제품 모델·문서 버전까지 정확히 연결하는지.
- 이미 있는 기능을 새 기능이라고 제안하지 않고 후보를 제외하는지.
- 다른 모델의 기능이나 상충 근거를 섞지 않고 보류/추가 확인하는지.
- 추가 설명서/조건으로 이전 후보가 무효가 되면 재조회·수정하고 이유를 남기는지.
- 채팅과 웹에서 같은 프로젝트·후보·근거·변경 이력을 다시 불러오는지.

모든 항목이 일반 LLM의 불가능한 업무라고 주장하지 않는다. **같은 조건에서 오류를 줄이고 작업을 재현/검토하기 쉽게 만드는 실제 효용**이 방어 논리다. A6000 네 장·모델 수·토큰 요금·테스트 수는 그 효용의 대체 지표가 아니다.

### 우선3 — 세 예시가 장식이 아니라 실제 실행이 되도록

| 신청서 예시 | 시연에서 확인할 판단 | 성공 증거 |
|---|---|---|
| 냉장고 청소/구조 개선 | 선반 분리 기능과 식품을 모두 옮기는 부담을 구분 | 두 근거를 대조한 잔여 불편·콘셉트/요구사항·검사 기록 |
| 식기세척기 안내 서비스 | 제품 기능 부족과 사용자가 안내를 찾기 어려운 문제를 구분 | 기존 안내/기능 대조와 실제 남은 문제에 맞는 서비스 제안 |
| 전자레인지 기능 중복 제외 | 이미 지원되는 기능을 새 콘셉트에서 제외 | 후보 제외/보류와 근거; 문서 추가/조건 변경 후 수정 |

합성자료는 통제된 오류·분기 검증에 사용하고, 가능한 범위의 실제 공개 리뷰/설명서 쌍은 별도로 근거·사용 조건을 확인해 확보한다. 합성자료로 실제 고객 수요나 신제품 실현성을 입증했다고 표현하지 않는다. 샘플 준비는 분석·검사·수정을 고정 출력으로 바꾸는 이유가 아니다.

### 우선4 — 효과와 재실행을 입증

일반 LLM/우리 Agent에 같은 입력·자료·모델/설정·출력 예산을 주고, 개발 예시와 분리한 입력을 가린 검토로 평가한다. 근거 정확성·모델 혼동·기존 기능 중복·보류/수정 대응·업무 완주율, 사람 검토/수정 시간, 전체 호출/재시도·토큰·지연을 측정한다. 미측정은 null로 남긴다. 상대 보고서의 좋은 점인 기준선 비교와 실패 기록을 우리도 적용한다.

깨끗한 환경에서 샘플 자료를 넣고 Skill/API/MCP/웹을 재실행하는 코드 ZIP·README·실제 시연 영상이 일치해야 한다. 모델/자료/코드 버전을 고정하고, 영상만 작동하거나 별도 준비 출력만 보여주는 상태를 피한다. 현재의 평가 수집 도구·준비 ZIP·웹 CI 성공은 실제 Agent 성능·최종 제출 증거가 아니다.

## 7. 참고할 것과 확장 판단

참고할 점은 좁고 구체적인 반복 업무, LLM과 계산 모듈의 분리, 원문 링크와 숫자/차트를 같이 검토하는 화면, 내용/모델/prompt 버전 캐시, 실패 실험에 따른 방법 전환, 업무 묶음별 독립 PR이다.

우리에 적합한 보완 후보는 근거 원문 미리보기·모델/버전별 기능 대조표·문서 변경에 따른 후보 영향 표시·검토 가능한 산출물 내보내기다. 이는 이미 있는 기획 검토 흐름을 강화하는 방향이다. 범위/계약/검수 조건을 검토한 뒤 채택해야 하며 본 보고서만으로 확장 채택 상태를 만들지 않는다. 정수기 사업 예측·대규모 마케팅 크롤러·실가전 제어를 단지 상대에게 있다는 이유로 추가할 근거는 없다.

공개 LICENSE가 확인되지 않아 코드를 자유 재사용할 수 있다고 가정하지 않는다. 이번에는 아이디어/구조를 조사했으며 코드 복사를 하지 않았다. 실제 오픈소스 도입은 공식 라이선스·버전·실측 선택 절차를 유지한다.
